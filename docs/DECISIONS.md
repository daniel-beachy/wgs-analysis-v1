# Architecture decision record

Each entry gives the decision, the alternatives considered, and why. Newest at the bottom.

## ADR-001 Code, data and results live in separate sibling folders

- **Decision:** `Genomics/WGS` (inputs, treated as read-only), `Genomics/wgs-analysis-v1` (code, git), `Genomics/wgs-data` (workspace).
- **Why:** inputs are never modified, so the provider checksums stay valid. Code can be public without risking data leaks. The workspace can be deleted and rebuilt.
- **Inputs are read-only:** where a tool needs a file next to an input (for example a `.tbi` index), we write it to the workspace. htslib's `file.vcf.gz##idx##index.tbi` syntax points the tool at it.

## ADR-002 Inputs are discovered by content, not by path

- **Decision:** walk the configured search roots and classify files by magic bytes and headers (VCF `##contig` lengths identify the build; CRAM headers provide the sample, M5 tags and programs). Configuration is layered: CLI > environment > `wgs.local.toml` (with per-host sections) > defaults relative to the repo.
- **Alternatives:** a fixed folder layout (brittle across machines); absolute paths in a config file (breaks when the drive letter or mount point changes).
- **Why:** the same drive is mounted as `/Volumes/Daniel_SSD` on macOS and as `D:\` on Windows. The GIAB demo sample has a completely different layout.

## ADR-003 Reproducible environment with pixi (conda-forge + bioconda)

- **Decision:** a single `pixi.toml` and lock file provide Python, DuckDB, pysam, bcftools/samtools/htslib and OpenJDK (for PharmCAT, RTG vcfeval, snpEff and Haplogrep, which are Java and therefore cross-platform).
- **Alternatives:** Homebrew plus pip (not reproducible, and pins drift); Docker (heavy on macOS, and the user has no Linux machine); uv only (cannot provide bcftools or samtools).
- **Environment location:** the env is *detached* (`.pixi/config.toml`) and lives on the host disk. The exFAT drive has no hardlinks and uses 256 KB clusters, so a conda env with tens of thousands of small files would waste gigabytes and run slowly. Envs are architecture-specific anyway.

## ADR-004 No Linux machine required

- **Decision:** everything runs natively on Apple Silicon. Benchmarking uses RTG `vcfeval` (Java) rather than hap.py (Linux and Python 2 only). CYP2D6 uses Cyrius (pure Python). Polygenic scores are computed in DuckDB rather than with pgsc_calc (Nextflow). If outputs from those Linux tools ever exist, they are ingested.

## ADR-005 exFAT-aware storage

- macOS writes `._*` AppleDouble files on exFAT, so discovery, git and data loading ignore them.
- 256 KB clusters make many small files expensive, so results are stored as a few large columnar files rather than thousands of JSON shards.
- exFAT reports every file as executable, so the git `core.fileMode=false` setting and ruff EXE rules are disabled.

## ADR-006 Privacy model

- Local only for now: no hosting, no portfolio link. The GitHub repo is public and contains code only.
- `scripts/data_guard.py` runs as a pre-commit hook. It blocks genomic file types, files over 2 MB, genotype-like rows and strings listed in `[guard].forbidden_strings` (for example the kit ID).
- In the UI, serious findings (ACMG SF genes, APOE ε4) are shown behind a click-to-reveal panel with context.

## ADR-007 Columnar variant store (Parquet + DuckDB)

- **Decision:** the VCF is normalised once (`bcftools norm -m -any`) and written to zstd Parquet, sorted by chromosome and position, in 100k-row groups. All analyses and the viewer query it with DuckDB (native in Python, WASM in the browser).
- **Why:** a single portable file, about 85 MB for 7.3M records, that any OS or architecture can read. Sorted row groups let DuckDB prune by region, so a full-genome aggregate takes under a second. Parquet is an open standard that will still be readable in 10 years.
- **Detail:** when a multiallelic site is split, the allele not carried (e.g. allele 1 at a `0/2` site) produces a meaningless `0/0` PASS row. These rows are dropped. RefCall and NoCall rows are kept, so "tested and reference" can be told apart from "not called".
- **Alternatives:** keeping the bgzipped VCF with tabix (needs htslib, and is slow for aggregates); SQLite (row-oriented, about 10× larger, slow for scans); a DuckDB database file (one writer, and its format still changes between versions).

## ADR-008 Rebuilding the CRAM reference

- The provider CRAM has no `M5`/`UR` tags, and tellmeGen did not supply its reference (`GRCh37.primary_assembly.par_y_masked`). Its contig names and lengths match Ensembl GRCh37 release 75 `primary_assembly` with a `chr` prefix, `chrM` (rCRS, 16569) and `GL*.1` scaffolds.
- **Decision:** download Ensembl r75 and check it against Ensembl's `CHECKSUMS`. Rename the contigs and N-mask the chrY PARs. Write the contigs in CRAM header order.
- **Verification (both must pass before anything uses the reference):**
  1. Decode reads from 3 random 200 kb windows on every main contig and from every scaffold. htslib verifies each CRAM slice's reference MD5 while reconstructing sequence.
  2. `bcftools norm --check-ref` must find 0 VCF REF mismatches.
- **Full proof (optional, one-time):** the `reference_full` stage decodes every read (`samtools view -u | samtools view -c`) and writes `full_decode.json`. On this dataset it decoded 868,564,724 reads with 0 MD5 mismatches.
- If verification fails, the CRAM-dependent stages (coverage, alignment stats) are skipped. Everything else still works from the VCF.

## ADR-009 Re-runnable stages with stamps

- `wgs run` runs a fixed list of stages. Each one writes a stamp: stage version, input size and mtime, and parameters. Unchanged stages are skipped, `--force` reruns them, and failures write tracebacks to `logs/<stage>.log`.
- Large temporary files go to internal-disk scratch (`$WGS_SCRATCH` or `$TMPDIR`), not the exFAT drive.
- Coverage uses `mosdepth --fast-mode` with quantized bins (0, 1–4, 5–9, 10–149, 150+). The VCF is not a gVCF, so the callable BED is what separates "homozygous reference" from "not covered" at any position.

## ADR-010 Learning first

- **Principle:** the tool is for someone who is curious and learning about their own genome. That shapes every section and every UI decision.
- **In practice:** every metric, term and finding gets a plain-language explanation that you can reach in one hover or click: tooltips, "what does this mean?" expanders, small diagrams, and links into `docs/GENETICS_PRIMER.md`. Jargon is always defined where it first appears. Each claim shows its evidence and confidence in words, not just as a score. Reports explain *why* something matters, or why it probably doesn't.

## ADR-011 Releases, an in-browser query engine and a tiny launcher

- **Releases:** the `publish` stage turns working files into an immutable release: `wgs-data/releases/<YYYY-MM-DD_HHMMSS>/manifest.json` plus content-keyed files in `releases/objects/` (`<name>-<hash>.parquet|json`, each with its sha256). Keys hash the table name, transform version and input fingerprint, so unchanged tables are shared between releases, not copied. A new release is written only when something changed, and each manifest links to its `previous` one. This is the basis for "What changed" (Steps 3 and 10): two releases can be diffed table by table. `index.json` lists releases newest first.
- **Viewer:** a static Svelte 5 + TypeScript app. Parquet tables are queried in the browser with **DuckDB-WASM** over HTTP range requests, so even the 7.3M-row variant table is never loaded whole. Page loads take about 1–2 s, filtered queries about 0.1–0.8 s. JSON documents (QC, coverage…) feed the charts. Charts are hand-written SVG components (no chart library). The genetics primer is bundled and its glossary drives every tooltip (ADR-010). Mermaid loads only on the Learn tab. Two details matter for this. First, this DuckDB-WASM build defaults to downloading whole files, so `db.ts` opens the database with `forceFullHTTPReads: false` and `reliableHeadRequests: true`. Without these, every page load fetched about 350 MB; with them, Health opens in under 1 s. Second, the Parquet reader extension is vendored in `viewer/public/duckdb-ext/` and loaded through `custom_extension_repository`, so the dashboard works offline and does not depend on the DuckDB CDN staying the same for a decade. When upgrading `@duckdb/duckdb-wasm`, download the matching `v<duckdb>/wasm_eh/parquet.duckdb_extension.wasm`.
  - *Why:* the same build runs on any OS and CPU with no install. Results stay as open formats (Parquet/JSON) that remain queryable outside the app, and the SQL tab exposes them directly.
  - *Alternatives:* Streamlit/Dash/Shiny (need a Python or R runtime on every laptop; not architecture-neutral); Electron/Tauri (heavy, or platform-specific toolchains); pre-rendered static HTML (no search over 7M rows); Datasette (Python runtime).
- **Launcher:** a dependency-free Go program, cross-compiled from the Mac for Windows x64 (`-H windowsgui`, icon via go-winres) and macOS (universal arm64 + x86_64 `.app`, ad-hoc signed). It embeds the built viewer, finds `wgs-data/releases` by walking up from its own location (or `--data` / `WGS_RELEASES`), serves both on `127.0.0.1` with Range support, opens the default browser, and refuses dotfiles and AppleDouble `._*` files. Port 8787 is preferred; if another instance already answers, it just opens a browser tab. The page sends a heartbeat every 10 s and the launcher exits about 75 s after the last one.
  - *Why a local server at all:* browsers block `fetch`/WebAssembly workers from `file://` pages, so double-clicking an `index.html` cannot work reliably. A single static binary is the simplest thing that works on both laptops with nothing installed.
  - DuckDB-WASM's "eh" bundle is used, which needs no cross-origin isolation headers.
- **Builds** run on the analysis Mac (`pixi run build-dashboard`) in internal scratch space, because exFAT has no symlinks for `node_modules/.bin`. Node and Go come from the pixi environment.

## ADR-012 Local knowledge store, refreshed by version

- **Privacy rule:** knowledge is downloaded and joined to your variants **on this computer**. Variants are never sent to web APIs (no VEP REST, no MyVariant.info). Links out (gnomAD, ClinVar, dbSNP) are only opened if you click them.
- **Sources (all free; versions are recorded per release):**

  | Source | Used for | Size | Update cadence |
  |---|---|---|---|
  | ClinVar (GRCh37 VCF) | Classifications, review stars, conditions | ~180 MB | Weekly |
  | Ensembl GFF3 GRCh37.87 | Gene models for `bcftools csq`; gene search | ~50 MB | Frozen (GRCh37) |
  | ClinGen gene validity + dosage | How strong each gene–disease link is; inheritance | ~2 MB | Daily export, rebuilt only on content change |
  | 1000 Genomes phase 3 sites (v5b, NCBI mirror — EBI is ~30× slower) | Overall and continental allele frequencies | ~2 GB | Frozen |
  | gnomAD v2.1.1 (slivar gnotate) | Popmax AF across about 140k people | ~2.2 GB | Frozen for GRCh37 |

- **Store:** `wgs-data/knowledge/<source>/<version>/` holds Parquet tables. `knowledge/index.json` records the upstream URL, Last-Modified/ETag/size fingerprint, build time and table checksums of each version, plus which version is *current*. A refresh `HEAD`s each source and rebuilds only those whose fingerprint changed. It builds into `.building/` and renames on success, so a failed download never corrupts the current version. The last 4 versions are kept, and the current one is never pruned. `--pin clinvar=YYYYMMDD` reproduces an archived ClinVar release, which makes past results reproducible.
- **Consequences:** `bcftools csq` (haplotype-aware, about 1 minute genome-wide) with Ensembl GFF3. *Rejected:* VEP with a 24 GB cache (too heavy for a portable drive) and snpEff (needs Java plus a 1 GB database, and its HGVS doesn't add much here). echtvar would be ideal for gnomAD, but it has no GRCh37 archive and no osx-arm64 build. slivar's gnotate zip provides the same lookup.
- **Release diff:** `publish` records the knowledge versions and evidence-model version in each manifest, and computes `changes.json` against the previous release. It lists sources whose version changed, claims added, removed or changed (field by field), and every ClinVar reclassification among your alleles. The diff is computed *after* the release digest, so it can never trigger a release on its own.
- **Why:** this fulfils "not a snapshot". Each finding traces back to a dated source version, and each change has a visible cause.

## ADR-013 Evidence model: two grades, weaker wins

- **Problem:** a variant "meaning something" depends on two independent questions. How strong is the published evidence for its effect? And is your genotype really there? A strong ClinVar classification on a low-quality call is not a strong finding, and neither is a perfect call of a 0★ assertion.
- **Decision:** every claim (`claims` table) carries an **evidence grade** (Strong / Moderate / Limited), a **call confidence** (High / Medium / Low / Not callable) and an **overall** grade = the weaker of the two. Each grade has a list of plain-language **reasons** and a list of **sources** with versions. Rules live in `src/wgs/evidence.py` (`MODEL_VERSION`). Changing a rule bumps the version, and the release diff shows its effect like a data update.
- **Evidence grade (v1, ClinVar-based claims):**
  - Review stars: 3–4★ → Strong; 2★ → Moderate; 0–1★ → Limited.
  - *Drug response* caps at Moderate until checked against CPIC/DPWG (Step 5). *Conflicting* → Limited.
  - Pathogenic or likely pathogenic, with population allele frequency (gnomAD popmax, otherwise 1000 Genomes) ≥ 5% → Limited (ACMG BA1). ≥ 1% → down one step (BS1-like).
  - Gene–disease validity in ClinGen *Disputed/Refuted* → Limited. *Limited* → down one step.
- **Call confidence:**
  - Non-PASS → Low.
  - GQ ≥ 30 and DP ≥ 15 → High. GQ ≥ 20 and DP ≥ 10 → Medium. Otherwise Low.
  - Unexpected read balance (het outside 20–80%, hom < 80%) → down one step.
  - Disagreement with the provider's genotype file (SNVs) → Low.
- **Which variants become claims:** ClinVar pathogenic, likely pathogenic, risk factor, association, protective and drug response; conflicting only when a submitter said pathogenic. VUS and benign are never claims; they stay visible in the variant explorer.
- **Routing to sections:**
  - Drug response → Medicines.
  - Association → Traits.
  - Pathogenic, likely pathogenic or conflicting in one copy of a gene whose ClinGen inheritance is recessive-only → Carrier.
  - Everything else → Health.
  - Steps 4–6 add curated claims (ACMG SF genes, CPIC diplotypes, GWAS/PGS traits) with their own evidence rules into the same table.
- **Sensitive findings:** pathogenic or likely pathogenic, and anything in genes such as *BRCA1/2*, *APOE*, *HTT* and *PRNP*, are masked until you click to reveal (per browser session). Each comes with a note that most such findings in healthy people are carrier status, low penetrance or misclassification, and need clinical confirmation.
- **Alternatives considered:** a single numeric score (hides *why*); full ACMG/AMP automated classification such as InterVar (it over-calls without the lab evidence, and is still a black box to a learner); copying ClinVar labels verbatim (ignores call quality and population frequency, both of which caught real problems in testing).

## ADR-014 Health and carrier: inheritance, per-lab conditions, actionability and predictions (evidence model v2)

- **Problem:** with v1, a ClinVar "pathogenic" label went straight into a claim. Three things made that misleading for one person's genome. (1) ClinVar's merged record names every condition any lab mentioned, and some labs list every disease of the gene, so a variant known for recessive hearing loss also showed the dominant skin syndromes that other variants in its gene cause. (2) Whether one copy matters depends on how the *specific* condition is inherited, not on the gene. (3) Rare variants no lab has classified were invisible, even when every predictor agrees they are damaging.
- **Decision:**
  - **Curated knowledge added** (all downloaded and joined locally): Mondo (disease names and cross-references), HPO and Orphanet (inheritance per disease, gene–disease links), ClinGen dosage and actionability, the ACMG SF v3.3 gene list with each gene's reporting rule (`src/wgs/knowledge/data/acmg_sf_v3.3.csv`), and ClinVar's per-lab `submission_summary` (about 6.8M submissions).
  - **Which condition is meant:** for each variant, each lab submission votes for the conditions it names. Submissions naming one or two conditions count; gene-wide lists do not. Conditions with at least 20% of the top condition's support are kept; the rest are shown as "also listed". The "Who says so" table shows every lab, its verdict and date.
  - **Inheritance:** per condition from HPO/Orphanet via Mondo cross-references, falling back to the gene's modes. Combined with zygosity and sex chromosome this gives a **role**: *carrier*, *affected* (both copies, or the only X copy), *possible* (dominant), or *unknown*. Mixed genes (a recessive condition and a dominant one in the same gene) get a per-condition role and a statement that explains both. Only "disease-like" claims (P/LP, conflicting, predicted) get a role; risk factors and associations don't.
  - **Routing:** disease-like and carrier role → Carrier; otherwise Health groups *monogenic*, *compound* (two P/LP variants in one recessive gene — flagged as "possible", since we can't tell if they're on different copies), *predicted*, *uncertain* (conflicting) and *risk* (risk factor, protective, low penetrance). Blood-group "phenotypes" go to Traits.
  - **ACMG SF:** a P/LP claim in a listed gene is *reportable* only if it meets the gene's rule (biallelic for recessive genes, *HFE* only homozygous C282Y, *TTN* only truncating). The `acmg_genes` release table also records the callable fraction of each gene, so "no findings" comes with how much was actually readable.
  - **Computer predictions** (AlphaMissense, REVEL, gnomAD v4.1 constraint) apply only to rare (< 0.1% in every population), PASS variants in known disease genes that ClinVar hasn't classified (or calls benign). Flag if LoF in a gene with LOEUF < 0.6 or a recessive gene, or if REVEL ≥ 0.644 and AlphaMissense > 0.564 agree, or if REVEL alone reaches the "strong" level (≥ 0.932), or (when REVEL has no score) AlphaMissense ≥ 0.9. Always **Limited**: predictors are about 90% accurate on known variants, which still yields many false alarms across a genome. Thresholds follow Pejaver et al. 2022 (ClinGen SVI calibration).
- **Rebuilds:** changing a knowledge source's parsed `schema` forces a rebuild on the next refresh; changing claims logic bumps the annotate stage version so `wgs run` re-annotates automatically.
- **Alternatives considered:** OMIM (best inheritance data, but licensed — HPO/Orphanet cover the same diseases openly); automated ACMG classification such as InterVar or CPSR (over-calls without lab evidence and hides the reasoning); CADD instead of REVEL (genome-wide but less calibrated for missense; its licence also forbids redistribution); SpliceAI (useful, but the precomputed scores need an Illumina login — a candidate for later).

## ADR-015 Pharmacogenomics: PharmCAT with outside calls, GRCh37 positions lifted one by one

- **Problem:** turn the genome into drug-gene results a clinician would recognise, with the published guideline behind each one. Four complications: the data is GRCh37 while PharmCAT only accepts GRCh38; *CYP2D6* cannot be read from a VCF (pseudogene *CYP2D7*, deletions, duplications, hybrids); HLA types need a dedicated typer; and the guidelines change several times a year.
- **Decision:**
  - **PharmCAT 3.4** (the CPIC/ClinPGx reference implementation, used by clinical labs) does diplotype calling, phenotype translation and guideline matching. It runs as a pinned jar from the knowledge store (`pharmcat` source), which also supplies its ~1,200 defining positions. Upgrading PharmCAT is a knowledge refresh, so new guidelines show up on **What changed** like any other source.
  - **No whole-VCF liftover.** PharmCAT warns that lifted VCFs give wrong calls (strand flips, missing reference blocks). Instead each defining position is lifted on its own (UCSC chain), its REF is checked against our verified GRCh37 FASTA (swapped REF/ALT handled), and the genotype is written from our own data: a variant if called, a confident reference *only if the position is callable*, otherwise missing. Missing positions are reported per gene, so "not found" never silently becomes "normal". The 1,226 positions and their status are published as `pgx_positions`.
  - **Outside calls:** *CYP2D6* from the CRAM via **Cyrius** (copy-number aware; run in its own pixi environment, about 20 min); HLA-A/B (and class II for later steps) from the CRAM via **T1K** against IPD-IMGT/HLA (`imgt_hla` source); *MT-RNR1* from mitochondrial variants, where coverage "HIGH" counts as callable. Pre-computed Cyrius/T1K outputs dropped into the WGS folder are ingested instead, so Linux users can run the tools elsewhere.
  - **Grading:** evidence is **Strong** for genes with a CPIC guideline and **Moderate** otherwise (DPWG-only); FDA label text is shown but not graded. Call confidence is **High** from callable VCF positions, lowered for missing positions, and **Medium** for Cyrius/T1K. Cyrius was validated on Illumina data, not DNBSEQ. Overall is the weaker of the two, as everywhere else (ADR-013).
  - **"Guidance differs" vs "standard":** *superseded by ADR-016* (buckets now follow ClinPGx's curated flags, not the wording). Originally: a guideline row was *action* when PharmCAT flags a dosing change or alternative drug, unless its text was a recognised "use standard dose" phrase. *CFTR* rows never count as action when the *CFTR* result is reference: those guidelines only apply to people with CF. Result for this genome: 52 action rows and 101 standard rows.
  - Genes whose guidelines use the genotype directly (VKORC1, CYP4F2, IFNL3) are labelled "Genotype reported", not "No result".
- **Alternatives considered:** Stargazer/Aldy/StellarPGx (more genes from BAMs, but less maintained or with licence limits; Cyrius is the most accurate open *CYP2D6* caller in published benchmarks); a full CrossMap VCF liftover (rejected per PharmCAT's own guidance); HLA-HD or OptiType (HLA-HD needs registration; OptiType is class I only and needs a MILP solver; T1K is MIT-licensed, fast and covers both classes); hand-maintaining CPIC tables (PharmCAT already packages them, versioned).
- **Licences:** PharmCAT MPL-2.0; ClinPGx data CC BY-SA 4.0; IPD-IMGT/HLA CC BY-ND 4.0; Cyrius GPLv3 (run as a separate tool, not linked); T1K MIT.

## ADR-016 No hand-written medical content; buckets from curated flags; release self-checks

- **Problem:** one question about warfarin exposed two bugs and a hand-written note in the viewer. An audit of all 397 guideline rows then found the "standard" test (a regex on the recommendation's wording) wrongly filed DPWG venlafaxine ("It is not possible to offer… Avoid venlafaxine"), codeine, tramadol and propafenone as standard. The viewer also held hand-written one-line descriptions of all 23 medicine genes. Hand-written text can't be refreshed, cited or checked, and won't scale to the next sections.
- **Decision:**
  - **No medical statements written into the app.** Everything the dashboard says about a gene, drug or variant comes from a versioned knowledge source and carries its citation. The viewer may contain teaching text (what a metaboliser type is) and presentational labels, never lookup tables of medical facts keyed by gene or drug. A test (`tests/test_checks.py`) fails if such a table reappears.
  - **Gene descriptions:** MedlinePlus Genetics (written for the public, expert-reviewed; bulk XML) first, then NCBI Gene's summary. RefSeq and OMIM summaries are curated; Alliance summaries are machine-generated, can describe an unrelated overlapping product (MT-RNR1's describes the humanin peptide), and so are shown collapsed and labelled. The official gene name is always shown. Published as `gene_about`.
  - **Drug buckets from structured flags.** ClinPGx curates three flags on every recommendation: `dosingInformation`, `alternateDrugAvailable` and `otherPrescribingGuidance`. **Guidance differs** = either of the first two; **Worth knowing** = only the third (monitoring, "if no response, switch", a dose calculator), or a drug-level note with no single recommendation (CPIC warfarin's flowchart); **Standard** = none, or the guideline says "no recommendation". **Not for your result** = a guideline or label exists, but has no advice for this genotype; such drugs are listed rather than hidden. Only CPIC/DPWG rows set the bucket: FDA label flags describe the label, not the person (desflurane's label is flagged even for a normal *RYR1*). When CPIC and DPWG disagree, the drug takes the more cautious bucket and shows "guidelines differ". Result for this genome: 35 differ, 23 worth knowing, 47 standard.
  - **Release self-checks.** `src/wgs/checks.py` holds SQL rules run on each release's own tables before publishing: findings are sourced, graded and uniquely identified; drug-response findings are never hidden as sensitive; common variants (> 5%, ACMG BA1) are never graded above Limited for disease; matched guidelines have text; buckets match the flags; notes come only from guidelines; every medicine gene has a sourced description. Results go into `checks.json` and the Data quality tab. A failure doesn't block a release (the rest of the data is still useful) but is shown prominently. On their first run they caught two real bugs: duplicate finding ids (DPWG publishes separate per-gene rows for the same drug) and PharmCAT data caveats being treated as drug advice. **Every future bug gets a check**, so it can't return silently.
- **Alternatives considered:** keep a better regex (wording varies across guideline sources and versions; the flags are curated for exactly this purpose); write gene descriptions by hand or with an LLM (not citable or refreshable); fail the release on a check failure (would leave the user with nothing after a knowledge refresh; showing the failure is more useful).
- **Licences:** MedlinePlus and NCBI Gene are US-government works in the public domain.


## ADR-017 Traits and polygenic scores: PGS Catalog + 1000 Genomes percentiles (evidence model v3)

- **Problem:** traits, common-disease risk and brain-related results come from many small effects, not one classified variant. They need a different source, a different way to compute "your result", and a different evidence grade, still with no hand-picking that can't be explained.
- **Decision:**
  - **Single-variant traits** come from the GWAS Catalog (EBI): a short featured list (`knowledge/data/gwas_featured.csv`) of variants with large, replicated effects that people can check against themselves. Your genotype is read with the PGx genotyper (so "no variant" at a well-covered site counts as a call). The effect direction is read from the Catalog's own convention: a "unit increase/decrease" note marks a per-copy β; otherwise the number is an odds ratio. The share of people with your genotype comes from 1000 Genomes allele frequencies (Hardy–Weinberg). Where the Catalog does not record the effect allele, the result is shown but graded Limited.
  - **Polygenic scores** come from the PGS Catalog. **Selection rule** (`knowledge/pgs.py: select`): for each trait, the single-trait score tested by the most *independent* publications, then the most independently tested people, then the most tested people, then the newest. About 45 featured traits get a page section and body system; every other trait with at least one independent test is browsable. Two pins override the rule, each with a reason in the CSV: multiple sclerosis (PGS002726: the rule's top picks split the genome into an HLA-only and a non-HLA score, so a whole-genome score is the fairer summary) and age-related macular degeneration (PGS004606: the rule's pick is the African-ancestry-trained twin of this European-trained score; swap if the Ancestry section shows a different closest population).
  - **Computing percentiles** follows pgsc_calc (the PGS Catalog's own pipeline) step by step, run locally with `pgscatalog-utils` and `plink2` in a separate pixi environment: QC the 1000 Genomes reference (GRCh37 harmonised panel, KING-related samples removed), build a target file of your genotypes at every score position (callable reference sites included), project you onto the reference PCs, normalise and match each scoring file, score you and the panel, then `ancestry-adjust` picks the most similar super-population and reports your empirical percentile in it.
  - **`--keep_ambiguous`:** pgsc_calc drops strand-ambiguous (A/T, C/G) SNPs by default because array data may be on either strand. Here both your calls and the harmonised scoring files are on the GRCh37 forward strand, so they are kept; without this 14 of 140 scores fell below the 75% match threshold.
  - **Evidence model v3** (`evidence.py`): GWAS single variants: Strong ≥ 3 publications, Moderate 2, Limited 1, or if below genome-wide significance, or if the effect allele is unknown. Polygenic scores: Moderate when ≥ 2 independent publications tested it in ≥ 20,000 people, otherwise Limited — **never Strong**, because a score shifts odds modestly and never diagnoses. Call confidence: High ≥ 90% of variants matched, Medium ≥ 75%, else Not callable (and no percentile is shown). Each score shows its best evaluation (independent first, then one reporting an effect size, then the largest).
  - **Brain & mind** is its own section with a caveats panel (weak prediction, confounding by family environment for education/cognition scores, European bias). Rare damaging-predicted variants in SFARI Gene genes are listed, always Limited, mirroring the Health page's prediction rules.
  - **Self-checks:** trait positions lift sanely, every trait and score is graded, direction-unknown SNPs are Limited, match rates of scored scores ≥ 75%, percentiles are within 0–100, every featured score is scored, no score is Strong, genotype calibration (see below), and score spread (across ≥ 20 scores the mean z must be within ±0.5 and the SD within 0.6–1.5; a systematic genotyping error shows up as a shifted or squashed distribution long before any single score looks odd).
  - **Stand-ins (alternates):** the rule also records the next two ranked scores for each featured trait. If the rule's pick cannot be scored on your data (match rate below 75%), the first stand-in that does score takes its place, and the page says so ("Stands in for X …"). This is how LDL cholesterol (rule pick PGS000814, 16 variants, 62.5% matched) is handled without a hand-made exception.
  - **Indels near other variants count as missing, not "no variant":** WGS callers can describe the same insertion/deletion at a slightly different position or as part of a larger multi-base change. Counting the panel's site as "0/0" in that case biased indel calls (18% "0/0" at sites where > 99% of people carry the variant). A panel indel with any of your indels within 25 bp, or inside a multi-base change, is now treated as missing (pgsc_calc mean-imputes missing variants). After the fix indels match SNPs (0.5% "0/0" in that band). The check `pgs.genotype_calibration` keeps this honest on every run: at sites where > 99% of the panel carries a variant, fewer than 2% of your calls may say you do not.
  - **Practical details:** matching runs in batches of at most 400 MB of compressed scoring files, because pgscatalog-match holds every file in memory and 220+ scores were killed on a 16 GB Mac; each score is matched on its own, so results are identical. Reference-panel scoring first copies only the variants the matched scorefiles use (~3 GB instead of the 7 GB, 78 M-variant panel) to the internal disk, once per run (≈ 5 min), then scores each chunk from it (≈ 2 min instead of 30–75 min; verified to give the same sums to the last printed digit). Panel scores do not depend on your genotypes, so they are also cached by a hash of the scoring file and panel version. Panel variants without an ID (`.`) are handled by passing the scoring file's own IDs to plink with `--extract`. macOS writes hidden `._*` files on exFAT drives; every file listing in the stage skips them. plink is given half the machine's memory so a 16 GB laptop does not swap.
- **Alternatives considered:** HIrisPlex-S for eye/hair/skin colour (model parameters are not published; the web tool would send genotypes off the machine, breaking the privacy rule); running pgsc_calc itself (Nextflow + containers; not portable to Windows and heavier than the pieces it wraps); one hand-picked score per trait (not refreshable or explainable); comparing to all 1000 Genomes samples (percentiles shift with ancestry for technical reasons).
- **Cost:** first run ≈ 2–3 hours on a 16 GB Mac with the data on an external SSD (reference QC 14 min and score normalising 34 min are cached per panel/catalog version; matching ≈ 40 min uses ~10 GB of temporary space on the internal disk; scoring the reference panel ≈ 20 min via a subset copy, cached). Re-runs after a catalog refresh redo only normalise/match and the scoring of changed score files; re-runs on the same catalog take minutes.
- **Licences:** GWAS Catalog and PGS Catalog metadata are EMBL-EBI open data; each scoring file's licence is recorded with the score. 1000 Genomes is open access. SFARI Gene data is free for research use.


## ADR-018 Verification audit: exact sources, live re-checks, ACMG BA1, and risk in absolute numbers (evidence model v4)

- **Problem:** before adding more sections, a review of every finding asked three things: does each finding link to the exact record it came from, does that record still say what we say, and what does a result mean in real outcomes ("8 in 100 vs 1 in 100", not "1.4× odds")? The review found eight bugs: the F5 Leiden site read backwards (GRCh37's reference carries the Leiden allele); a "belongs to the rarer allele" note that contradicted ClinVar on alt-major sites; common alleles (≥ 5%) given carrier/affected labels; protein changes in nonstandard notation; VUS wording claiming no lab had classified a variant ClinVar lists as uncertain; intergenic GWAS hits with no gene; brain variants without sources; and PGS cards saying "N variants found" when they meant positions readable.
- **Decision:**
  - **Exact records.** Every finding's `sources` lists the record (ClinVar VCV, GWAS Catalog GCST + PubMed, PGS Catalog PGS/PPM, SFARI gene page, gnomAD variant, MANE transcript). Protein changes are HGVS on the MANE Select transcript (Ensembl/NCBI MANE v1.x) and name the transcript with its version. Self-checks enforce that each claim links to a record (a URL with an id, not a home page), brain variants and trait variants are sourced, and protein names match `^p\.`.
  - **ACMG/AMP BA1** (`evidence.too_common`): an allele at ≥ 5% in any population is too common to cause a rare Mendelian disease on its own, so carrier/affected labels are withheld (role "Too common to cause it alone") and the evidence grade drops to Limited. ClinVar expert-panel/practice-guideline records (3★+) are exempt because ClinGen already weighed frequency (its BA1 exception list includes HFE C282Y). Self-check `claims.ba1_role`.
  - **Live audit** (`wgs audit`, `src/wgs/audit.py`): re-fetches every cited ClinVar record (classification + review stars; "changed upstream" when ClinVar re-evaluated it after our snapshot), GWAS Catalog association (study + effect allele), PGS Catalog score (trait + publication), PubMed citation (title), a sample of links, and every curated quote (below). The report goes to `wgs-data/audits/` and a summary beside the releases (`releases/audits/<id>.json`) that the Data quality tab shows. It needs internet, so it is a command rather than a pipeline stage; run it after every refresh. First run: ClinVar 264/264, PGS Catalog 141/141, PubMed 134/134, GWAS Catalog 15/15 matched; 1 dead link (an HPO purl that now redirects to a removed page), fixed by linking ontology terms through EBI OLS.
  - **Absolute risk for polygenic scores** (`src/wgs/absrisk.py`) — two automated routes and one curated input:
    1. *From discrimination (AUROC)*: AUROC is unit-free, so it can be converted without knowing how the study scaled the score. Under the binormal liability model, `d = √2·Φ⁻¹(AUROC)` and the risk at your z is solved exactly against the baseline K. Only evaluations whose covariates are purely technical (ancestry PCs, genotyping batch), with ≥ 1,000 people and ≥ 100 cases, for the score's own disease (not a subtype, special population or "10-year risk" model), and in the ancestry you were compared with, are used — independent studies first, then the largest.
    2. *From a per-SD odds or hazard ratio*: only where a curated row confirms the ratio is per standard deviation (≈ 0.6% of PGS Catalog records say so; the field has no unit). The logistic model is calibrated so the population average equals K (Gauss–Hermite integration); hazards use `1 − exp(−H·e^{βz})`.
    3. *Baseline K*: a cited lifetime risk from `knowledge/data/baseline_risk.toml` (each row: value, CI, age window, population, source URL, PubMed id and the exact quoted sentence) — else the evaluation cohort's own case share, labelled as such, only when the cohort was not enriched for cases (≤ 20% cases).
    The card shows "≈ X in 100 people with your score (range from the effect's CI) vs Y in 100 typical", the ratio, both sources with links and quotes, the method, and a reminder that lifestyle and family history matter as much. Otherwise it says **not established** with the specific reason. Sex-specific scores show "not applicable" for the other sex. Self-check `pgs.abs_risk_sourced`; the audit's `curated` check confirms each quote's numbers still appear at its source.
  - **Single-variant findings:** for P/LP findings where you may be affected, the ClinGen Actionability expert panel's likelihood score is shown as a band ("5 to 39 in 100 people with a disease-causing genotype develop …", with its evidence grade A–D). ClinVar gives no effect size for risk factors, so no number is invented for them.
- **Alternatives considered:** OR per allele × population risk for every variant (ClinVar has no ORs; GWAS ORs are per allele and not additive for monogenic variants); using PGS Catalog ORs as if per SD (the unit is usually unknown; a per-quintile OR read as per-SD inflates risk several-fold); taking lifetime risks from a single global source such as GBD (licence and age-window mismatches); an LLM summary per finding (not citable or checkable).
- **Known limitation:** pathogenic variants where GRCh37's reference carries the disease allele (F5 Leiden-type) are absent from ClinVar's GRCh37 VCF and so can't be found from your VCF alone; the F5 card explains this.
- **Addendum (hardening after the first full audit):**
  - *A value must be in its quote.* A baseline row is used only if its quoted sentence states the value (as a percent, per 1,000/100,000 or "1 in N"); rows whose quote only pointed to a supplement, or whose value was derived by us (e.g. summing subtypes), were removed.
  - *Per-SD rows need four confirmations:* the PGS Catalog performance record (PPM) reports the same ratio (±0.005); its cohort ancestry matches yours; its covariates are only age, sex or technical terms; and the paper's quoted text says the ratio is per SD. The "not established" reason names the rule that failed. Effects confirmed this way are labelled "per standard deviation of the score" everywhere; other ORs/HRs say "between score groups" or "comparison not stated in the PGS Catalog".
  - *Gene-specific penetrance only from single-gene ratings.* ClinGen sometimes rates several genes together (121 of 443 reports); a band from such a report is not shown for any one gene; the card says which genes it was shared with. Self-check `claims.penetrance_single_gene`.
  - *Audit robustness.* Transient failures (PMC stub pages, Ensembl 504s, NCBI 400s) are retried before being reported; numbers are normalised (Lancet middle dots, thin spaces, HTML entities) before matching quotes.


## ADR-019 Polygenic scores per trait: median across studies, full range, agreement label

- **Problem:** each trait showed one score, chosen by the selection rule (ADR-017). When the rule's pick is an outlier, the page shows the outlier. Example: intelligence came out at the 99th percentile (PGS004427, tested once, by its own authors) while the two next-ranked scores gave the 92nd and 64th. The stand-ins were already computed on every run but hidden.
- **Decision:**
  - **Show every computed score.** `pgs_scores` keeps the rule's pick and its stand-ins (`trait_group`, `rank_in_trait`, `pgp_id`). Nothing extra is computed; the stand-ins were already scored.
  - **Headline = median across studies.** For each trait, take each study's (PGS Catalog publication's) median percentile, then the median of those. Several scores from one paper (e.g. three methods on one GWAS) count once, so one study can't outvote the others by publishing more variants of the same score. With two studies the median is their midpoint.
  - **Range** = the lowest to highest percentile of every computed score, shown as a band with a tick per score.
  - **Agreement label** from every score's z (so two methods from one paper that disagree are not hidden by that paper's median): *agree* when all lie within `AGREE_SPREAD_SD` = 1 standard deviation (≈ the gap between the 50th and 84th percentile); *agree on direction* when they differ by more but all sit on the same side of average; otherwise *disagree*. The text adds when the scores come from fewer studies than scores ("all from one study, so this is not an independent confirmation"). The threshold is a display rule, not a medical one.
  - **Risk in numbers** (ADR-018) comes from one score's published effect, so it uses the most-tested score (selection-rule order) whose absolute risk could be established, and names it ("it is that one score's estimate, not the median's").
  - **Grade shown on the trait** = the best-tested score's overall grade; every score's own evidence and call grades are listed beneath it, with its paper (PubMed and DOI) and PGS Catalog record.
  - New table `pgs_traits` (one row per trait). Self-checks: `pgs.trait_headline` (recomputes median, range and counts from `pgs_scores`), `pgs.trait_risk_named`, `pgs.sourced` (every computed score links to its paper); `pgs.featured_scored` now checks traits.
- **Alternatives considered:** the mean percentile (pulled by one extreme score); the median of all scores without grouping by study (three variants from one paper outvote two independent studies); keeping the single best-tested score as headline (still one score); scoring every PGS Catalog score for each featured trait (the original plan for step 7b; it needs a new multi-hour scoring run, so it is deferred).
- **Not changed yet:** the selection rule itself (which three scores are picked) and a flag for evaluations reporting R² above the trait's SNP heritability (needs a cited heritability source). Both change which scores are computed, so they wait for the next scoring run.


## ADR-020 Ancestry: calibrated continental shares, nearest reference population, mtDNA and Y haplogroups

- **Problem:** the Ancestry section should say which reference populations the genome is most like and read the maternal and paternal lineages, with the same honesty as the rest of the dashboard: how sure, and where the method can't tell. It must run on a 16 GB Mac without large new downloads.
- **Decision:**
  - **Reference:** the 2,504 people of the 1000 Genomes panel already used for polygenic scores, and the 10-component PCA the PGS stage computes with FRAPOSA (≈ 55,000 LD-thinned positions). Population names and sampling details come from the IGSR data portal (new knowledge source `igsr_populations`).
  - **Continental shares:** your PCA point is written as the closest mix of the five super-population centres (weights ≥ 0 summing to 1, solved exactly), the projection approach of rye (Conley et al., *Nucleic Acids Res* 2023). AMR is kept as a source even though its populations are themselves admixed, so Latin American ancestry shows as such rather than being forced into the other four.
  - **Calibration by leave-one-out:** every reference person is scored with themselves removed from the centres. A group's **noise floor** is the 95th percentile of the share it gets among reference people from other, non-admixed populations; a share at or below it is "not detected" and graded Limited. On the current panel, reference people get 94–100% of their own group on average, and floors run from 1.5% (African) to 9.7% (European, because South Asian people sit partly towards it). Grades: main group (≥ 50%, above floor) Strong, other detected shares Moderate, undetected Limited; call High with ≥ 50,000 PCA positions.
  - **Nearest population:** the 10 nearest reference people (PCs standardised within your main group) vote. A leave-one-out confusion matrix on the same rule decides what can be said: populations mixed up with the winner at least 20% of the time are reported together. In Europe, Finnish, Spanish and Tuscan are told apart 91–99% of the time; British and Utah-CEPH are not (44% and 75%), so a British/CEU result is reported as "British or CEU". Graded Limited when reported as a group, when its own accuracy is under 90%, or when the main group is under 80% of your ancestry; otherwise Moderate. Never Strong: these are sampled groups, not countries.
  - **Maternal line:** haplogrep3 (Schönherr et al. 2023) on the PASS chrM calls, tree PhyloTree 17 Forensic Update 1.2 (rCRS). Call High at quality ≥ 0.9, Medium ≥ 0.8. The two next-best fits are listed.
  - **Paternal line (XY only):** Yleaf v4.1.5 (Ralf et al. 2018) on the Y reads, YFull v14 tree. The Y reads are cut from the CRAM through its index first (≈ 20 s, 0.8 GB), because Yleaf's own CRAM route runs `samtools idxstats`, which reads all 53 GB. Without an alignment Yleaf reads the VCF and infers that absent positions match the reference; that result is capped at Medium. Call High at Yleaf QC-score ≥ 0.95 (its default threshold), Medium ≥ 0.9. Both lineages link to the branch on YFull's public tree (age estimates, related samples) instead of carrying hand-written descriptions (ADR-016).
  - **Tools** live in a separate `haplo` pixi environment. Yleaf is installed from its pinned GitHub release because the bioconda build omits the marker data and trees.
  - **Self-checks:** shares are valid and sum to 1; shares at or below their floor are never shown as found; the nearest-population vote counts exactly 10 neighbours; every haplogroup names its tool, tree, quality and link; haplogroup mutation lists contain no placeholders (an empty haplogrep field was once read as "nan" and counted as a missing mutation).
- **Alternatives considered:** supervised ADMIXTURE (closed-source binary, not on osx-arm64; the rye authors report estimates close to ADMIXTURE's for continental groups); HGDP + 1000 Genomes for finer regions (tens of GB and hours of computation, many groups of 15–30 people; planned as a later step); yhaplo for the Y chromosome (needs accepting 23andMe's non-commercial licence and uses a 2016 tree); hand-written haplogroup descriptions (ADR-016).
- **Licences:** 1000 Genomes and IGSR data are open; haplogrep3 is MIT; Yleaf is GPL-3.0 (run as a separate tool, not linked); PhyloTree and YFull trees are used for classification and linked, not redistributed.


## ADR-021 The hidden genome: specialised callers for what the VCF can't show

- **Problem:** a standard short-read VCF only holds small changes (under ~50 letters) in regions where reads map uniquely. Some of the most common and best-understood genetic findings live elsewhere: genes with a near-identical twin (*SMN1*, the commonest serious carrier finding; *GBA1*), repeat expansions (Huntington's, fragile X, myotonic dystrophy), and HLA types, which were typed for medicines (ADR-015) but not used for their disease associations. The information is in the aligned reads (CRAM); it needs different tools.
- **Decision:** a `special` stage re-reads these from the CRAM and turns them into ordinary graded findings (claims), plus a table of everything checked so "nothing found" is visible.
  - ***SMN1/SMN2*** with Illumina's SMNCopyNumberCaller (Chen et al., *Genet Med* 2020). 1 copy = carrier, 0 = affected, 2 with g.27134T>G = possible "silent" (2+0) carrier. When the tool can't decide (copy-number estimates between 1 and 2), the result is **Not determined** (call Not callable) with the clinical test that settles it (SMN1 qPCR/MLPA); it never falls back to "not a carrier". ACMG recommends offering SMA carrier screening to everyone (Gregg et al. 2021).
  - ***GBA1*** with Gauchian (Toffoli et al., *Commun Biol* 2022): pseudogene-derived recombinants, deletions and ~110 known disease variants.
  - **Repeat expansions** with ExpansionHunter (Dolzhenko et al. 2019) at every STRchive locus (Hiatt et al., *Genome Med* 2025; new knowledge source `strchive`, MIT licence, with its hg19 ExpansionHunter catalogue). Interpretation rules:
    - *Counts are compared relative to the reference genome.* The catalogue's regions sometimes include interruptions that clinical counts leave out (AR: 22 pure CAG, an interruption, 5 more), so a count goes to the clinical scale as the reference's longest pure run (capped at the top of the typical range, since the reference genome carries a typical allele and loose motifs such as GCN can absorb a flanking codon) plus the difference from the reference. Insertion-type loci, whose disease motif is absent from the reference, are counted directly. A clinical estimate is only *displayed* where the region is a clean repeat.
    - *Two callers agreeing.* Where the VCF has no length-changing call inside the repeat (confident or unsure) and ExpansionHunter is within one unit of the reference, the allele is the reference length: typical, call High.
    - *The call grade comes from ExpansionHunter's 95% interval:* High when the interval stays in the typical range, Medium when it reaches the intermediate range, Low when it reaches the disease range ("most likely typical, low confidence"), Not callable when no reads cover the repeat (e.g. very GC-rich *FMR1*). Out-of-range results are always Medium at best, with the reminder that sizes from short reads are estimates (sensitivity 97.3%, specificity 99.6% for expansions in Ibañez et al., *Lancet Neurol* 2022).
    - Evidence grade from STRchive's gene–disease rating (Definitive/Strong → Strong, Moderate → Moderate, else Limited); loci STRchive rates Disputed or Refuted are listed but not classified; loci with missing or inconsistent ranges are "not classified".
    - Adult-onset conditions (STRchive minimum age of onset ≥ 18) are click-to-reveal, names included (AGENTS.md §5.9).
  - **HLA associations** from a curated, quoted table (`knowledge/data/hla_associations.toml`, same policy as `baseline_risk.toml`: every row quotes its source word for word). Types come from T1K (two-field resolution). Rules: *risk* / *protective* (carrying any listed allele), *haplotype* (all listed alleles), *rule_out* (carrying none makes the condition very unlikely, e.g. coeliac disease without DQ2/DQ8). A rule that needs a gene T1K didn't type says nothing. Call High at T1K allele quality ≥ 20. No absolute risk is computed where the quoted sources don't give a consistent baseline (narcolepsy prevalence ranges 10–47 per 100,000); the card quotes the prevalence instead so a large odds ratio is read in context.
  - **Audit:** `wgs audit --only curated` now covers the HLA table and also checks that each cited first author matches PubMed (a mistyped author was caught while building this table).
  - **Licences:** Illumina moved SMNCopyNumberCaller, Cyrius and ExpansionHunter to the PolyForm Strict licence in December 2022. The versions pinned here (SMNCopyNumberCaller 1.1.2, ExpansionHunter 5.0.0, Cyrius 1.1.1) were released earlier under Apache-2.0, and Gauchian 1.0.2 under GPL-3.0; they are pinned to those releases. The tools live in a separate `special` pixi environment.
  - **Self-checks:** hard-to-read gene results name their tool, grades and sources; "not determined" is always Not callable; unreadable repeats are never typical; every out-of-range repeat is also a finding; every HLA association quotes a PubMed record.
- **Alternatives considered:** Paraphase (built for PacBio long reads, not short reads); yhaplo-style manual parsing of paralog positions (re-implements what the validated callers already do); Stranger's bundled thresholds (STRchive is curated with references and updated monthly); calling repeats from the VCF alone (DeepVariant can't size repeats longer than a read).
- **Blood group** (`knowledge/data/blood_group.toml`, quoted like the other curated tables):
  - *ABO:* the GRCh37 reference carries the O allele (c.261delG, rs8176719), so copies of the inserted base there = non-O alleles; the two B-specificity changes c.796C>A and c.803G>C (Yamamoto et al., *Nature* 1990) count B alleles; c.1061delC marks A2. Positions were checked against dbSNP's GRCh37 forward-strand mapping (ABO is on the reverse strand). Typing requires every deciding position to be readable, and the O position is re-counted directly from the CRAM as an independent check (a disagreement drops the call to Low). Genome-based typing was ≥ 99% concordant with serology (Lane et al., *Lancet Haematol* 2018).
  - *RhD:* RhD-negative is almost always two deleted RHD copies (Singleton et al., *Blood* 2000), so RHD copy number comes from the depth of confidently mapped reads (MAPQ ≥ 20) on RHD against its twin RHCE: ratio < 0.15 → none (RhD-negative), 0.3–0.7 → one, > 0.8 → two, otherwise not determined. The card quotes the exception: many RhD-negative people of African ancestry carry an inactive RHD copy (RHDψ) that depth can't see.
- **How your genome compares** (Overview): only counts whose definitions are close to the 1000 Genomes Project's "typical genome" (Auton et al., *Nature* 2015): variant sites (4.1–5.0 million), autosomal SNVs (EUR median 3.53 million) and protein-truncating variants on each gene's MANE Select transcript (149–182). Rare-variant and ClinVar counts are left out on purpose: the study's ~7× sequencing and different software dominate those differences.
- **Deletions and duplications in the 84 ACMG SF genes** (exons of each gene's MANE Select transcript, else its longest protein-coding transcript in Ensembl r87): the gene regions (± 5 kb) are cut from the CRAM through its index and checked two ways.
  1. *Breakpoint reads:* Delly (Rausch et al., *Bioinformatics* 2012) PASS deletions and duplications.
  2. *Exon depth:* mean depth of reads, divided by the panel median, then **corrected for GC content** against exons of similar GC (depth on this genome peaks at 45–50% GC and falls to about 0.7× at 25% and 70% GC, 0.24× at 80%). A depth signal needs the GC-corrected ratio below 0.65 (or above 1.40), at least 3 robust SDs from exons of similar GC, the same drop among *all* reads (a dip only in uniquely placed reads is a mappability artefact, e.g. TTN's triplicated I-band), and at least 2 neighbouring exons. Exons outside 25–75% GC give no depth signal and are counted as not judged.
  - A change is a finding (*possible exon deletion/duplication*, call Medium, evidence Moderate for deletions, Limited for duplications) only when both methods agree and it is below 1% in gnomAD-SV v2.1 (Collins et al., *Nature* 2020; new knowledge source `gnomad_sv`, CC0). Depth-only runs of ≥ 5 exons (what a whole-gene deletion with breakpoints outside the window looks like) are flagged for attention but never become findings; shorter depth-only signals are listed as noise. Findings are sensitive (click-to-reveal) and always point to clinical confirmation (MLPA or chromosomal microarray).
  - *First run:* 38 exons not judgeable (22 extreme GC, 16 low mappability). Before GC correction, 17 depth-only "signals" appeared, all at extreme-GC or hard-to-map exons; this is why depth alone is never reported.
  - *Limits:* a single genome has no comparison panel, so sensitivity for one-exon changes is modest; inversions and balanced rearrangements are invisible to this approach.


## ADR-022 Accuracy, part 1: re-count the raw reads behind every finding

- **Problem:** every genotype in the dashboard comes from tellmeGen's VCF (DeepVariant). No other variant caller runs natively on this Mac (DeepVariant is Linux/x86), and a genotype wrong at one important position makes everything built on it wrong. The provider's own genotype file (checked in QC) was made from the same calls, so it can't catch a caller that misread the reads.
- **Decision:** a `recount` stage, after all stages that write findings, goes back to the CRAM at every position a finding rests on and at every PharmCAT defining position (about 1,500 sites, ≈ 45 s), and counts read by read which version each read shows.
  - *Reads used:* not duplicate, secondary, supplementary or QC-failed; mapping quality ≥ 20. Reads below MAPQ 20 are counted separately: if they are ≥ 30% of the reads (and at least 3), the site is flagged as a **look-alike** region (a paralog or pseudogene).
  - *Single-letter changes:* the base at the position, quality ≥ 20.
  - *Insertions, deletions, multi-letter changes:* each whole read, soft-clipped ends included, is laid without gaps against both versions of the surrounding 600 letters (the reference and the reference with the variant applied), within 12 letters plus the indel length of its aligned start. It counts for the version it fits with at least 2 fewer mismatches (bases of quality ≥ 10). Reads that don't reach across the change fit both equally and are not counted; reads with more than 8 mismatches against both count as "other". This is the idea behind variant callers' read-to-haplotype scoring, without gaps or a likelihood model. Counting only reads whose alignment crosses the site missed every read carrying a long insertion, because the aligner soft-clips them; a test now covers that case.
  - *Genotype:* binomial likelihoods for 0, 1 or 2 copies (1 on the X outside the pseudo-autosomal regions and on the Y for XY), with a 2% chance per read of showing the other version by error (Li, *Bioinformatics* 2011, PMID 21903627). Reads of a second alternative allele at a split multi-allelic site are kept in the total.
  - *Verdicts:* **confirmed** when the most likely genotype is the call's, at least 100× likelier than the next (log10 ratio ≥ 2), from at least 8 reads; **weak** when it is the call's but below either bar; **disagrees** when it is a different genotype and passes both bars; **unclear** when different but below a bar; **not called** where the VCF gave no usable genotype; **not checkable** for mitochondrial DNA (hundreds of copies per cell), mismatched reference letters, or repeats wider than 100 letters. A two-sided Fisher test also flags variant reads on one strand only (p < 0.001, ≥ 6 variant reads).
  - *Effect on grades (in `evidence.recount_call`):* disagrees → call Low; weak, unclear, look-alike or one-strand → call at most Medium; confirmed → reason added; never raised. Overall is recomputed as the weaker grade. Medicine genes typed by PharmCAT take the worst verdict over their defining positions; genes typed by Cyrius or T1K (which read the raw reads themselves) are left alone. Positions the VCF left uncalled are reported on the gene as notes ("the raw reads suggest one copy") and never change the result.
  - *Publishing:* the stage writes re-counted copies of `claims` and `pgx_genes`; publish uses them only when they are newer than every source file, so a stale re-count can't hide a newer finding. A `recount` table (one row per site, with read counts) and document go into the release.
  - *Self-checks:* every positioned finding was re-counted; no finding the reads don't back keeps a High call; every PharmCAT gene was re-counted and lowered on disagreement; and at least 95% of re-counted genotypes match their call (a systematic counting bug, like the soft-clip one, would break this).
  - *First run:* 1,489 of 1,490 genotypes confirmed (271 behind findings, all 1,218 PharmCAT positions); the one exception was a call already graded Low. No grade changed.
- **Blood group, same step:** the ABO card also compares tellmeGen's own genotype file at the deciding positions (rs8176719 is written D/I there; D is the O allele). A disagreement lowers the call to Low. The RhD card says why that file can't help: it lists letters at single positions, and a gene missing on both copies leaves no letters to list.
- **What this can't do:** catch errors in the reads themselves (sample, library or sequencing errors), or variants the VCF missed at positions no finding uses. Measuring those needs a truth set: Genome in a Bottle HG002 (ADR-023).
- **Alternatives considered:** bcftools mpileup/call as a second caller (a real option for a later step; it would add discovery, but for checking known positions a transparent count is easier to explain and audit); local realignment with a gapped aligner (no aligner library in the environment, and gapless fitting against both versions handles the indels seen here); counting only reads that cross the site in their alignment (misses soft-clipped insertion reads, see above).


## ADR-023 Accuracy, part 2: Genome in a Bottle HG002 benchmark and a second variant caller

- **Problem:** ADR-022 checks that the variant caller read the reads correctly, but nothing yet said how often the re-count itself is right, how much harder some stretches of the genome are, or which variants the VCF missed. DeepVariant can't run on this Mac, so the owner's VCF can't be re-made; the methods that do run here can be measured on a genome whose answer is known.
- **Data (new knowledge source `giab`, public NIST data):** the HG002 truth set v4.2.1 on GRCh37, chromosomes 1–22, with its confident regions (Wagner et al., *Cell Genom* 2022, PMID 36452119); GIAB's genome stratifications v3.6, used as a map of hard-to-sequence stretches with a reason each (tandem repeats and homopolymers, segmental duplications, low mappability, GC < 25% or > 65%, the MHC, other difficult regions; Dwarshuis et al., *Nat Commun* 2024, PMID 39424793); and HG002's 2×150 DNBSEQ reads (GIAB's 100× BGIseq BAM, the same platform family as the owner's genome), streamed from GIAB's server only for the evaluated regions and thinned to 30× (115.6× before; `samtools view --subsample` with a fixed seed). Regions: the exons of the 84 ACMG SF genes and every PharmCAT defining position, ± 500 letters, merged (1,006 regions, 1.86 million letters; 1.81 million inside the truth set's confident regions). The regions' fingerprint is stored with the reads, and the build stops if it no longer matches (a tie between two *TNNT2* transcripts once made the exon list change between runs; ties now go to the lowest transcript ID and a test covers it).
- **Benchmark stage (`benchmark`)** measures two methods, both split into ordinary and hard-to-sequence stretches:
  1. *The read re-count* (ADR-022, same settings) at every true HG002 variant in the regions (1,962 alleles) claimed with its true number of copies, and at the same positions with wrong claims (one copy too many or too few), plus 4,000 ClinVar variants HG002 doesn't carry (2,500 single-letter, 1,500 insertions/deletions, at least 25 letters from any true variant, sampled by a fixed hash) claimed as one copy.
  2. *bcftools 1.24* (`mpileup -q20 -Q20 | call -m`, quality ≥ 30, left-aligned) as a second caller, scored against the truth with RTG Tools 3.13 `vcfeval` (Krusche et al., *Nat Biotechnol* 2019, PMID 30858580), which matches the same change written in different ways.
- **Results on HG002 at 30×:**
  - *Re-count:* 98.9% of correct calls confirmed (99.6% in ordinary stretches, 96.6% in hard ones); 98.7% of wrong claims caught (99.4% / 96.4%); wrong claims confirmed 0.10% (7 of 7,203: 0.02% ordinary, 0.35% hard). When the re-count gives a clear answer it is right 99.88% of the time. Single letters: 99.6% confirmed in ordinary stretches, 98.8% in hard ones, no wrong claim confirmed. Insertions/deletions in hard stretches are the weak spot: 92.7% confirmed, 0.96% of wrong claims confirmed. By reason: repeats 90.4% confirmed (1.0% of wrong claims through), GC-extreme 98.1%, low mappability 97.2%, segmental duplications 99.2%. Six of the seven errors are insertions/deletions in repeats; the seventh is a single-letter variant the truth calls one copy where 16 of 17 reads show it. The 10 long deletions (93 to 3,600 letters) are reported as not checkable.
  - *bcftools:* precision 97.9%, recall 97.8% overall; 99.7% / 99.2% in ordinary stretches; 93.7% / 94.5% in hard ones. Single letters in ordinary stretches 99.9% / 99.5%; insertions/deletions 96.3% / 95.2% in ordinary stretches, 86.5% / 87.1% in hard ones. Where the re-count also confirms a call, precision rises to 99.1% (97.3% in hard stretches).
  - *Seen in other people:* bcftools calls at sites gnomAD v2.1.1 flags as failing its own quality filters (Karczewski et al., *Nature* 2020, PMID 32461654) were real 3 times out of 13; at common sites (≥ 1% in gnomAD's highest population or 1000 Genomes) 98.7%; rare 96.8%; not in either 80% (16 of 20).
- **Decision on grades:** a finding inside a hard-to-sequence stretch gets a call reason that says so and why ("the same letter or short pattern repeated many times", …), but no grade cap. In those stretches the re-count let through 0.35% of wrong claims (1.0% in repeats), and weak or unclear re-counts already cap the call at Medium (ADR-022); a blanket cap would downgrade hundreds of confirmed calls to protect against a handful. The reason is attached in the re-count stage, so findings, medicine positions and the benchmark use one overlap rule.
- **Second caller on the owner's reads (`secondcall`):** the same bcftools command on the owner's CRAM in the same regions, compared with the VCF's PASS calls by vcfeval (genotype ignored, so only "present or not" counts). Every variant only bcftools finds is re-counted, checked against the hard-stretch map, ClinVar, gnomAD (including its filter flag) and 1000 Genomes, and joined to the VCF's own record there (NoCall = DeepVariant saw it but gave no genotype; RefCall = it looked and saw no variant). The reads' verdict: *reads show it* (clear re-count, at least one copy), *placed uncertainly* (same but look-alike or one-strand flags), *reads don't show it*, or *unclear*. These variants are leads, not findings: they get no annotation or grade and change nothing elsewhere. Clusters of differences gnomAD flags, with almost nobody homozygous at a 50% frequency, are the classic sign of reads from a look-alike copy; the re-count can't see that (it counts the same placed reads), which is why the gnomAD flag is shown next to it.
- **Self-checks:** the re-count confirms ≥ 98% of correct calls and confirms ≤ 0.5% of wrong claims in ordinary stretches; bcftools' precision ≥ 99% and recall ≥ 98% for single letters in ordinary stretches; every second-caller variant has a re-count verdict. A broken counting or scoring step would fail these.
- **Limits:** the benchmark covers chromosomes 1–22 only (the truth set's span), so X-linked genes such as *G6PD* aren't measured; only stretches inside GIAB's confident regions are scored, which leaves out the hardest places (where even GIAB's truth is unsettled); DeepVariant itself isn't benchmarked, because it can't run here; and these are one sample's numbers at one depth.
- **Alternatives considered:** running the whole HG002 genome (≈ 100 GB of reads; the question is about the genes findings come from); GATK HaplotypeCaller as the second caller (Java-heavy and slow on this Mac; bcftools is already in the environment and its errors are well understood); hap.py instead of vcfeval directly (Linux-only builds; the GA4GH method it implements uses vcfeval as its matching engine); capping grades in hard stretches (rejected, see above).
- **Addendum (gnomAD-flagged frequencies; evidence model v5):**
  - *Problem:* the annotate stage read gnomAD v2.1.1's highest population frequency through slivar, but not the flag slivar adds where gnomAD's own calls at a site failed its quality checks (its random-forest filter, InbreedingCoeff or AC0; Karczewski et al., *Nature* 2020, PMID 32461654). So a flagged frequency counted like any other: a flagged 44% could make a ClinVar-pathogenic variant "too common" (BA1) and withhold its carrier label, a flagged tiny frequency could read as "rare in gnomAD", and the majority-allele note could rest on either. Above, only 3 of 13 bcftools calls at flagged sites were real.
  - *Decision:* `annotations.gnomad_filtered` records the flag (also on `claims` and `brain_variants`; empty means the gnomAD file carries no flag, so the status is unknown). For grading, a flagged frequency is **unknown, neither high nor low** (`evidence.population_afs`): it can't trigger BA1/BS1 or withhold carrier/affected labels, and it can't show that a variant is rare, so at a flagged site a computer prediction or a Brain & mind entry needs a 1000 Genomes frequency below 0.1% (`evidence.is_rare`). 1000 Genomes frequencies still count. The majority-allele note ignores a flagged frequency. The frequency is still shown, labelled "gnomAD flagged this site", and an evidence reason says it wasn't used. The rule lives in `wgs.evidence`, so the evidence model moves to v5.
  - *Self-checks:* `annotations.gnomad_flag_read` (every allele with a gnomAD frequency has a flag status, and a whole genome has some flagged sites), `claims.gnomad_flag_not_graded` and `brain.gnomad_flag_not_rare`; `claims.common_is_limited` and `claims.ba1_role` use the same usable frequency.
  - *Result for this genome:* 99,659 of 4,648,970 alleles sit at flagged sites. No finding changed grade. One computer-prediction finding (Limited) was withdrawn: gnomAD flagged its site with no usable frequency, and 1000 Genomes has none, which the old rule read as "not seen, so rare". Two drug-response findings sit at flagged sites and now carry the label (frequency doesn't grade them). All 54 self-checks pass.
  - *Alternatives considered:* dropping the flagged frequency from the tables (it is the clearest hint that reads there may come from a look-alike copy, so it stays visible); lowering the call confidence at flagged sites (the flag is about gnomAD's calls, and the 3-in-13 figure is for bcftools on HG002, not the DeepVariant calls in your VCF, so it can't calibrate a call grade; a call reason without a grade change is a possible later step).
- **Addendum (demo release from the truth set; Step 9c):**
  - *Problem:* the dashboard holds the owner's genome, so it can't be shown to anyone else. HG002 is shared openly through the Personal Genome Project and its truth VCF is already in the knowledge store, but the pipeline assumed a sequencing run: reads, read depths and a provider genotype file. Graded by depth, every truth-set call would read as "thin support: 0 reads"; QC called a genome with no chrX records XY (0 of 0 heterozygous); the ancestry stage wrote column-less tables that broke its self-checks and the Ancestry page; and the Data quality page crashed without the provider-file comparison.
  - *Decision:* `config/demo.toml` builds a separate workspace (`wgs-data-demo/`, sample `HG002`) with `wgs demo` (`pixi run demo`). It borrows the owner's knowledge store read-only (`[paths] knowledge`; `wgs knowledge refresh` refuses there) and the rebuilt reference (`[inputs] reference`). `[truth]` names the truth set and marks the VCF as one:
    - **Input:** records inside the truth set's confident regions only, contigs renamed to `chr…`, and every per-sample field except GT and GQ dropped. The truth VCF's DP and AD are summed over many datasets and would read as one run's reads. On v4.2.1 that leaves 3.91 million records on chromosomes 1–22.
    - **Reference:** with no reads to decode, a provided FASTA is accepted only if its contigs match the VCF's and every REF allele matches (0 mismatches here).
    - **Callable map:** the confident regions, all `CALLABLE`, so "looked and found nothing" means "inside the regions the truth set vouches for".
    - **Call confidence (truth-set rule):** High, with the reason "Benchmark genotype from the <truth set>, which combines several sequencing technologies, inside the regions it is confident about (there are no reads to count here)". These genotypes are what the benchmark above measures accuracy against, and claiming read support that doesn't exist would be false. The rule applies only when `[truth]` is set (it enters the annotate stage's parameters only then), so the owner's grades and the evidence model version (v5) don't change. The 21,947 records without a GQ (all in the MHC; the truth set gives none there) count as missing wherever a stage requires a genotype quality (polygenic scores, medicine positions, the Brain & mind list).
    - **QC:** depth and allele-balance panels are left empty, and the sex call is unknown when there are no chrX records (the truth set covers chromosomes 1–22 only).
    - **Stages:** those that need reads or the provider file skip with their reason (`genotypes`, `fastq_stats`, `alignment_stats`, `reference_full`, `cyp2d6`, `hla`, `special`, `recount`, `secondcall`). Ancestry skips when there is no PCA and no mtDNA or Y record to place. Polygenic scores run only with `--pgs`, because the 1000 Genomes panel has to be re-scored for this genome's matched positions (hours).
    - **Dashboard:** the manifest's `truth_set` field (label, version, URL) makes every page show a "Demo" banner naming the sample and the truth set, and changes the footer. Sections whose stage was skipped say "No results in this release" instead of announcing a future step. The launcher answers `/api/ping` with a hash of the data folder it serves (`X-Genome-Data`) and reuses a running dashboard only when it serves the same folder, so the demo never opens on top of the owner's genome or the other way round.
    - **Runs work from their sample's scratch folder:** DuckDB spills to `.tmp` in the working folder under fixed file names. When the demo and the owner's annotate ran at once from the repo, they overwrote each other's spill files (both stopped with an I/O error) and spilled genome data landed in the public repo's folder.
  - *Self-checks and tests:* in the demo release every self-check passes or is skipped with the tables it needs (re-count, second caller, polygenic scores, ancestry, specialised callers). `tests/test_demo.py` runs a synthetic truth VCF through the input preparation and the variants, reference, coverage, QC and ancestry stages, and checks the read-only knowledge store, the scratch working folder and the `--pgs` opt-in. `tests/test_evidence.py` covers the truth-set rule, and `launcher/main_test.go` the same-folder reuse.
  - *Alternatives considered:* keeping the truth set's summed DP/AD (hundreds of "reads" from many runs would overstate one run's support); grading truth calls Medium as a hedge (nothing measures them as less sure, and the benchmark treats them as right); shipping HG002's reads (≈ 100 GB, and the point is a shareable release, not re-calling); a separate viewer build for the demo (one viewer reading the manifest keeps one code path); scoring polygenic scores by default (hours on this laptop for a page that is optional in the demo).

## ADR-024 Refresh: one command, and every change says why

- **Problem:** keeping the results current took three commands (`wgs knowledge refresh`, `wgs run`, then reading the new release), and "What changed" listed graded claims only. A medicine-gene type, a polygenic percentile or an ancestry share could move without a word, and no change said *which* update caused it, so a reader couldn't tell a reclassification in ClinVar from a change in this project's code.
- **Decision:**
  - *`wgs refresh`* updates every knowledge source, re-runs the stages they feed (the stamps of ADR-009 decide which), publishes, and prints the new release's summary, or "Nothing changed, so no new release". The PGS Catalog and its 1000 Genomes reference scoring are left alone unless `--pgs` is given: a newly selected score means hours of scoring the reference panel on this laptop. A source that fails to download is reported and the run goes ahead on its current version (the release records the versions it used), with a non-zero exit so a scheduled run notices.
  - *Why each change happened:* every added, removed, regraded or reworded finding carries `why`: the knowledge sources named in its own `sources` that moved to a new version, plus `evidence_model` when the grading rules changed. An empty list means neither moved, so the analysis itself changed (code or settings). The attribution is by provenance, not by experiment: a source the finding cites changed, which makes it the likely cause, not a proven one. The dashboard prints it under each row ("Because: ClinVar 2026-10-04 → 2026-10-19").
  - *Other results:* `diff.RESULTS` lists the result tables that aren't claims and the fields that matter in each: medicine genes (diplotype, phenotype, activity score), polygenic traits (percentile, agreement, grade), ancestry shares, haplogroups, hard-to-read genes and repeats, each with the knowledge sources it is built from. Rows are matched across releases by their key; numbers count as changed only past a tolerance (1 percentile point, 0.01 of an activity score or ancestry share), so floating-point noise from a re-run isn't news. The "What changed" page lists them in an "Other results" card with the same "Because" line, masking sensitive rows as elsewhere.
  - *Tables added or removed:* the document records which tables are new or gone, and the release summary says so ("new: highlights") instead of a bare "findings +0".
  - The changes document moves to schema 2 (`results`, `tables`, `why`); older releases keep their schema-1 documents (releases are immutable) and the page shows them as before.
- **Fix found on the first real refresh:** Genome in a Bottle's source (ADR-023) looked up the knowledge store through a stand-in object that broke outside the demo build, so its refresh failed. Sources now receive the store itself (`Source.store`); `tests/test_knowledge.py` fails on the old code.
- **First real refresh (2026-10-22):** five sources moved (ClinVar, ClinGen, MedlinePlus, Mondo, NCBI Gene); 2 findings were no longer reported (both attributed to ClinVar, one also to Mondo), 1 was reworded, none were regraded, no other result moved, and 3 of the owner's ClinVar variants were reclassified.
- **Tests:** `tests/test_diff.py` (attribution to a moved source, to the grading rules, and to neither; tolerances on numeric results; added and removed results; the summary of a release that only adds a table).
- **Alternatives considered:** re-running with one source changed at a time to prove each cause (as many full runs as sources moved; provenance already names the candidates); refreshing the polygenic-score sources by default (hours, for scores that change rarely); diffing every column of every table (noisy: most columns are inputs or display text, and float noise would flag everything).

## ADR-025 Highlights: the notable results from every section, picked by fixed rules

- **Problem:** the brief asks for "every place the genome reliably differs from a typical one, what it means and how sure we are, Strong to Limited". The results are spread over seven sections, each with its own layout, so there was no single page that answers "what stands out?". A hand-picked list would be editorial; a list ranked by anything other than evidence would put the least reliable results (polygenic percentiles) in the most prominent place, which is why the body map was dropped (PLAN, 2026-10-16).
- **Decision:** a `highlights` table built in `publish` from the release's own tables (`src/wgs/highlights.py`), so it can never disagree with them. Each row is a row of another table picked by one of these rules, with its statement, grades and sources copied unchanged:
  - *single-gene findings* (`claims`, Health, group `monogenic`) and *carrier results* (every `carrier` claim);
  - *computer predictions* (group `predicted`): kept, because they are where a rare change in a disease gene would first show up, but they are always Limited and labelled "a hypothesis";
  - *risk factors* graded at least Moderate (most common-variant risks are Limited and small; listing 50 of them would bury everything else);
  - *medicine genes* whose phenotype class isn't normal (poor, intermediate, decreased, increased, rapid, ultrarapid, positive), with the number of medicines whose CPIC/DPWG advice differs (`pgx_drugs.tier = 'change'` on a guideline row that matched the genotype, counted once per drug; FDA label rows never set a bucket);
  - *HLA associations* the HLA scan marks notable (you carry the type, or a rule-out type is absent);
  - *polygenic scores* for a featured trait (one with a section) at or below the 5th or at or above the 95th percentile (median across studies, ADR-019) whose studies don't disagree;
  - *single-variant traits* graded at least Moderate where fewer than 1 in 4 people share your genotype (`genotype_share` < 0.25);
  - anything the *hard-to-read-gene*, *repeat* (intermediate or disease range) and *deletion/duplication* (`possible_*`) scans flagged.
  Variants of uncertain significance are left out: they are not answers. Rows are ranked Strong → Moderate → Limited, then by kind (single-gene, hard-to-read, deletion, repeat, carrier, medicine, HLA, risk factor, polygenic, trait, prediction), then title. `notable_because` names the rule in words ("In the top 5%: the Nth percentile (median across studies)", "About N in 100 people share your genotype"); for claims it is the first evidence reason.
- **Dashboard:** the Highlights page shows one card per row (kind, title, statement, why it's here, both grades, up to three source links, a link to the section with the full evidence), filterable by grade, with sensitive findings hidden until revealed as elsewhere, and the rules listed at the bottom.
- **Self-checks:** `highlights.match_source` (every highlight taken from a claim points at an existing claim and has the same overall and evidence grade) and `highlights.complete` (every highlight has a grade, a reason, a statement, a source and a unique id). `tests/test_highlights.py` checks each rule's inclusions and exclusions, the ranking, and that the self-check catches a highlight whose grade was raised.
- **First run:** 29 highlights (12 Strong, 7 Moderate, 10 Limited).
- **Alternatives considered:** a body map (dropped, see PLAN); ranking by effect size (would rank polygenic scores and risk factors whose effects are least certain highest); letting the AI pick the highlights (not reproducible; the AI's reading is kept separate, ADR-026); including every risk factor (dozens of Limited rows with small effects).

## ADR-026 Claude's take: an AI-written reading of the highlights, labelled as opinion

- **Problem:** the highlights say what stands out, one result at a time; they don't say how the results fit together or which are worth acting on first, which is what a person new to genetics most wants. That needs judgement, and ADR-016 rules out hand-written medical text in the pipeline. Generating it inside the pipeline would need an API key and send results to a cloud service on every run.
- **Decision:** the take is the one exception to ADR-016, and it is fenced in:
  - *Written outside the pipeline and the repo:* in a Claude Code session, into `<workspace>/notes/take.md` (the private data folder). Front matter names the `author`, the date `written` and the release it was `written_for`. Nothing is generated during a run, and the genome isn't sent anywhere by the pipeline.
  - *Every paragraph and list cites:* results are cited as `[[table:key]]` (a highlight, claim, medicine gene, polygenic trait, trait variant, HLA association, hard-to-read gene, repeat, deletion/duplication, ancestry group or haplogroup). `publish` (`src/wgs/take.py`) parses the markdown into headings, paragraphs and lists with plain, bold, italic and citation segments only, checks that every block cites, and looks up every citation in the new release. Problems (an uncited paragraph, a citation that isn't in the release or names a table that can't be cited) are printed during the run and listed above the take on the page.
  - *Stale when the results move:* for each citation the grade and statement (or the table's equivalent fields) in the release it was written for are compared with the new release; if any differ, or that release is unknown, the take is marked stale and the page says so. A knowledge refresh therefore flags the take for rewriting instead of silently leaving old reasoning next to new results.
  - *Shown as opinion:* the card carries an "Opinion" label and the line "This is an AI's reading of your highlights, not a rule-based result … trust the result and its grade over the wording here". Each citation renders as a chip with the cited result's current title and grade, linking to it.
- **Tests:** `tests/test_take.py` (parsing, citation checks, the three kinds of problem, staleness when a cited grade changes, no take written).
- **Limits:** the pipeline checks that the take cites real results, not that its sentences are a fair reading of them; that rests on the author and on the reader following the chips. It is written for one person and is never part of the demo unless one is written for HG002.
- **Alternatives considered:** generating the take with the Claude API during `publish` (needs a key and an upload of results on every run; a reproducible release would depend on a model's output); no take at all (leaves the "so what?" to the reader, which the brief asks us to help with); free text without citations (can't be checked or kept current).

## ADR-027 AI helpers: a read-only MCP server and an "Ask AI" button

- **Problem:** AGENTS.md lets an assistant with a shell read the results through `wgs query`, but assistants without one (Claude Desktop and other chat apps) can't, and even with a shell every question is a quoted command. A person reading the dashboard who wants to ask about one result has to retype it, and loses the grades, reasons and sources that make an answer responsible.
- **Decision:**
  - *`wgs mcp`* (`src/wgs/mcp_server.py`) is a Model Context Protocol server over stdio: JSON-RPC 2.0, one message per line, started by the assistant as a subprocess. It offers tools only: `guide` (AGENTS.md), `overview` (release, knowledge versions, self-check counts, tables and documents; not the sample ID), `highlights`, `result` (every column of one row, by a citable table and its key, the same ones a take can cite, ADR-026) and `query` (one SELECT, at most 1,000 rows). It answers protocol versions 2025-06-18, 2025-03-26 and 2024-11-05 (the client's if supported, otherwise the newest). Its `instructions` tell the assistant to read the guide first and summarise AGENTS.md §5.
  - *Same sandbox as `wgs query`:* both go through `src/wgs/readonly.py`. Tables are views over the release's Parquet files and JSON documents are `doc_<name>` views; DuckDB may read only the releases folder, external access is off and the configuration is locked, and only a single SELECT is accepted. The FASTQ, CRAM and VCF are outside that folder, so they can't be reached. The release is reopened on every call, so a release published while the assistant is connected is picked up.
  - *Errors are the assistant's to fix:* a bad query comes back as a tool result marked `isError` with the message, not as a protocol error, so the assistant can correct its SQL.
  - *Claude Code offers it in this repo* through `.mcp.json`, which each user approves once; README shows `claude mcp add` and the Claude Desktop config for use elsewhere.
  - *"Ask AI" button* on every highlight and every finding's details: copies one result as a prompt (title, statement, why it was highlighted, overall grade, evidence and call grades with their reasons, source links, and its table and key) followed by AGENTS.md §5 condensed into six rules (plain language, separate the science from the call, absolute numbers only where sourced, carrier ≠ affected and Limited = hypothesis, not a diagnosis and never a medication change, cite and flag uncertainty). For a highlight, the reasons are looked up on the row it came from. In the demo the prompt says the genome is the public reference sample, not the reader's. The rules are guidance to the assistant, not medical text, so ADR-016 is unaffected.
- **Privacy:** the server sends nothing anywhere itself, and the button only fills the clipboard. But whatever an assistant reads travels to wherever its model runs: with a cloud model, the rows it queries or the result pasted are shared with that provider. The guide and server instructions ask for narrow queries over bulk dumps, and the button's tooltip says that pasting into a cloud assistant shares that one result.
- **Tests:** `tests/test_mcp.py` (handshake and version negotiation, notifications get no reply, unknown methods are refused, every tool on a fixture release, writes, multiple statements and reading a file outside the releases folder are all refused, and `serve` answers one JSON message per line).
- **Alternatives considered:** the official MCP Python SDK (another dependency in a pinned environment for a few dozen lines of protocol; worth revisiting if resources or prompts are needed); an HTTP transport (a listening port, even on 127.0.0.1, is more exposure than a pipe to a subprocess the assistant starts); exposing the raw files (against the privacy model, ADR-006); tools that write or re-run the pipeline (releases are immutable, and results must come from rules, ADR-016); an "Ask AI" button that calls a model directly (needs a key and sends the result without the person choosing where).

## ADR-028 A public demo on GitHub Pages

- **Problem:** the dashboard is meant to be shown (a portfolio card), but the owner's release must never leave the machine (ADR-006), and the HG002 demo release (Step 9c) was too big for a static host: its `annotations` file was 137 MB, over the 100 MB GitHub accepts per file and Cloudflare Pages' 25 MiB. Some knowledge sources also allow only non-commercial use.
- **Decision:**
  - *Only a truth-set release can be exported.* `wgs --config config/demo.toml export-site --out DIR` (`src/wgs/site.py`) refuses any release whose manifest has no `truth_set`, and any whose sample matches an ID from the personal config. It then searches every output file, string columns of every table included, for the personal config's private strings (`[guard] forbidden_strings` and the sample ID), and deletes the export if one turns up. Absolute paths on this Mac inside JSON documents (the QC report names the reference FASTA) are cut down to the file name.
  - *Smaller, then split.* `annotations` loses five columns: `revel` and `am_score` (REVEL is free for non-commercial use only, and AlphaMissense is CC BY-NC-SA 4.0, so their scores aren't republished in bulk; the few graded findings that quote a score keep it, with its source), and `gnomad_popmax_af_controls`, `gnomad_nhomalt` and `gnomad_nhomalt_controls`, which no page shows. Allele frequencies become single precision. Any table over 20 MB is rewritten with Parquet V2 encodings, sorted by position, and split into parts by whole chromosomes, so DuckDB skips parts by their statistics. For the 2026-10-22 demo, the export is 117.5 MB in 33 files: `annotations` in 5 parts and `variants` in 2, none over 20 MB. The viewer's own DuckDB WebAssembly file (36 MB) is the largest file on the site, fine for GitHub Pages but not for Cloudflare Pages.
  - *The manifest says what changed.* A split table lists its `parts`; `path` points at the first. An `export` section records the source release, the dropped columns with their reasons, and the split tables. `index.json` lists only the exported release. A rewritten table says it is stored in position order (`sorted_by`). The viewer reads every part of a table (`read_parquet([...])`), and the variant explorer leaves out ORDER BY for such a table, so DuckDB keeps file order and stops after the first page instead of reading every row group: over the web, where each read is a round trip, the first page had taken 17 s on the live site, and takes 1.3 s on a test server that adds 100 ms to every request. With no launcher behind it, the first refused heartbeat stops the timer.
  - *Hosting follows the owner's other projects:* a GitHub Pages project site at `daniel-beachy.github.io/wgs-analysis-v1/`, deployed by `.github/workflows/pages.yml`. The repo holds code only, so the data travels as `demo-site.tar.gz`, an asset of a GitHub release tagged `demo-data-<release id>`. The workflow builds the viewer, adds the newest such asset and deploys. It runs when `viewer/` or the workflow changes, or on demand. `pixi run demo-site` exports, packs, uploads and starts a deploy (`--no-upload` stops after packing). The site needs HTTP range requests, which GitHub Pages serves for Parquet files.
- **Licences:** everything else on the site is public domain, CC0, CC BY, MIT or open data (README, "Knowledge sources") and is attributed where it's shown. ClinPGx guideline text stays CC BY-SA 4.0. HG002 is NIST data from a Personal Genome Project participant who consented to public sharing. The site is non-commercial, like the project.
- **Tests:** `tests/test_site.py` (a release without `truth_set`, or with a private sample ID, is refused; columns are dropped and frequencies narrowed; local paths are cut; a table splits into one part per chromosome that together give back every row, in order, and is marked `sorted_by`; a private string anywhere stops the export and leaves no files).
- **Alternatives considered:** committing the data to a `gh-pages` branch (genomic data, even public, in the repo's history, against its "code only" rule); the portfolio repo (would grow by 120 MB per update); trimming rows (the variant explorer would silently show part of the genome); one 83 MB file (fits GitHub but no other host, and leaves no headroom); Cloudflare Pages (25 MiB limit on DuckDB's own WebAssembly file).
