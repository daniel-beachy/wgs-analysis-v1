# Architecture decision record

Each entry gives the decision, the alternatives considered, and why. Newest at the bottom.

## ADR-001 Code, data and results live in separate sibling folders

- **Decision:** `Genomics/WGS` (inputs, treated as read-only), `Genomics/wgs-analysis-v1` (code, git), `Genomics/wgs-data` (workspace).
- **Why:** inputs are never modified, so the provider checksums stay valid. Code can be public without risking data leaks. The workspace can be deleted and rebuilt.
- **Inputs are read-only:** where a tool needs a file next to an input (for example a `.tbi` index), we write it to the workspace. htslib's `file.vcf.gz##idx##index.tbi` syntax points the tool at it.

## ADR-002 Inputs are discovered by content, not by path

- **Decision:** walk the configured search roots and classify files by magic bytes and headers (VCF `##contig` lengths identify the build; CRAM headers provide the sample, M5 tags and programs). Configuration is layered: CLI > environment > `wgs.local.toml` (with per-host sections) > defaults relative to the repo.
- **Alternatives:** a fixed folder layout (brittle across machines); absolute paths in a config file (breaks when the drive letter or mount point changes).
- **Why:** the same drive is mounted as `/Volumes/Daniel_SSD` on macOS and as `D:\` on Windows. The GIAB demo sample has a completely different layout.

## ADR-003 Reproducible environment with pixi (conda-forge + bioconda)

- **Decision:** a single `pixi.toml` and lock file provide Python, DuckDB, pysam, bcftools/samtools/htslib and OpenJDK (for PharmCAT, RTG vcfeval, snpEff and Haplogrep, which are Java and therefore cross-platform).
- **Alternatives:** Homebrew plus pip (not reproducible, and pins drift); Docker (heavy on macOS, and the user has no Linux machine); uv only (cannot provide bcftools or samtools).
- **Environment location:** the env is *detached* (`.pixi/config.toml`) and lives on the host disk. The exFAT drive has no hardlinks and uses 256 KB clusters, so a conda env with tens of thousands of small files would waste gigabytes and run slowly. Envs are architecture-specific anyway.

## ADR-004 No Linux machine required

- **Decision:** everything runs natively on Apple Silicon. Benchmarking uses RTG `vcfeval` (Java) rather than hap.py (Linux and Python 2 only). CYP2D6 uses Cyrius (pure Python). Polygenic scores are computed in DuckDB rather than with pgsc_calc (Nextflow). If outputs from those Linux tools ever exist, they are ingested.

## ADR-005 exFAT-aware storage

- macOS writes `._*` AppleDouble files on exFAT, so discovery, git and data loading ignore them.
- 256 KB clusters make many small files expensive, so results are stored as a few large columnar files rather than thousands of JSON shards.
- exFAT reports every file as executable, so the git `core.fileMode=false` setting and ruff EXE rules are disabled.

## ADR-006 Privacy model

- Local only for now: no hosting, no portfolio link. The GitHub repo is public and contains code only.
- `scripts/data_guard.py` runs as a pre-commit hook. It blocks genomic file types, files over 2 MB, genotype-like rows and strings listed in `[guard].forbidden_strings` (for example the kit ID).
- In the UI, serious findings (ACMG SF genes, APOE ε4) are shown behind a click-to-reveal panel with context.

## ADR-007 Columnar variant store (Parquet + DuckDB)

- **Decision:** the VCF is normalised once (`bcftools norm -m -any`) and written to zstd Parquet, sorted by chromosome and position, in 100k-row groups. All analyses and the viewer query it with DuckDB (native in Python, WASM in the browser).
- **Why:** a single portable file, about 85 MB for 7.3M records, that any OS or architecture can read. Sorted row groups let DuckDB prune by region, so a full-genome aggregate takes under a second. Parquet is an open standard that will still be readable in 10 years.
- **Detail:** when a multiallelic site is split, the allele not carried (e.g. allele 1 at a `0/2` site) produces a meaningless `0/0` PASS row. These rows are dropped. RefCall and NoCall rows are kept, so "tested and reference" can be told apart from "not called".
- **Alternatives:** keeping the bgzipped VCF with tabix (needs htslib, and is slow for aggregates); SQLite (row-oriented, about 10× larger, slow for scans); a DuckDB database file (one writer, and its format still changes between versions).

## ADR-008 Rebuilding the CRAM reference

- The provider CRAM has no `M5`/`UR` tags, and tellmeGen did not supply its reference (`GRCh37.primary_assembly.par_y_masked`). Its contig names and lengths match Ensembl GRCh37 release 75 `primary_assembly` with a `chr` prefix, `chrM` (rCRS, 16569) and `GL*.1` scaffolds.
- **Decision:** download Ensembl r75 and check it against Ensembl's `CHECKSUMS`. Rename the contigs and N-mask the chrY PARs. Write the contigs in CRAM header order.
- **Verification (both must pass before anything uses the reference):**
  1. Decode reads from 3 random 200 kb windows on every main contig and from every scaffold. htslib verifies each CRAM slice's reference MD5 while reconstructing sequence.
  2. `bcftools norm --check-ref` must find 0 VCF REF mismatches.
- **Full proof (optional, one-time):** the `reference_full` stage decodes every read (`samtools view -u | samtools view -c`) and writes `full_decode.json`. On this dataset it decoded 868,564,724 reads with 0 MD5 mismatches.
- If verification fails, the CRAM-dependent stages (coverage, alignment stats) are skipped. Everything else still works from the VCF.

## ADR-009 Re-runnable stages with stamps

- `wgs run` runs a fixed list of stages. Each one writes a stamp: stage version, input size and mtime, and parameters. Unchanged stages are skipped, `--force` reruns them, and failures write tracebacks to `logs/<stage>.log`.
- Large temporary files go to internal-disk scratch (`$WGS_SCRATCH` or `$TMPDIR`), not the exFAT drive.
- Coverage uses `mosdepth --fast-mode` with quantized bins (0, 1–4, 5–9, 10–149, 150+). The VCF is not a gVCF, so the callable BED is what separates "homozygous reference" from "not covered" at any position.

## ADR-010 Learning first

- **Principle:** the tool is for someone who is curious and learning about their own genome. That shapes every section and every UI decision.
- **In practice:** every metric, term and finding gets a plain-language explanation that you can reach in one hover or click: tooltips, "what does this mean?" expanders, small diagrams, and links into `docs/GENETICS_PRIMER.md`. Jargon is always defined where it first appears. Each claim shows its evidence and confidence in words, not just as a score. Reports explain *why* something matters, or why it probably doesn't.

## ADR-011 Releases, an in-browser query engine and a tiny launcher

- **Releases:** the `publish` stage turns working files into an immutable release: `wgs-data/releases/<YYYY-MM-DD_HHMMSS>/manifest.json` plus content-keyed files in `releases/objects/` (`<name>-<hash>.parquet|json`, each with its sha256). Keys hash the table name, transform version and input fingerprint, so unchanged tables are shared between releases, not copied. A new release is written only when something changed, and each manifest links to its `previous` one. This is the basis for "What changed" (Steps 3 and 10): two releases can be diffed table by table. `index.json` lists releases newest first.
- **Viewer:** a static Svelte 5 + TypeScript app. Parquet tables are queried in the browser with **DuckDB-WASM** over HTTP range requests, so even the 7.3M-row variant table is never loaded whole. Page loads take about 1–2 s, filtered queries about 0.1–0.8 s. JSON documents (QC, coverage…) feed the charts. Charts are hand-written SVG components (no chart library). The genetics primer is bundled and its glossary drives every tooltip (ADR-010). Mermaid loads only on the Learn tab. Two details matter for this. First, this DuckDB-WASM build defaults to downloading whole files, so `db.ts` opens the database with `forceFullHTTPReads: false` and `reliableHeadRequests: true`. Without these, every page load fetched about 350 MB; with them, Health opens in under 1 s. Second, the Parquet reader extension is vendored in `viewer/public/duckdb-ext/` and loaded through `custom_extension_repository`, so the dashboard works offline and does not depend on the DuckDB CDN staying the same for a decade. When upgrading `@duckdb/duckdb-wasm`, download the matching `v<duckdb>/wasm_eh/parquet.duckdb_extension.wasm`.
  - *Why:* the same build runs on any OS and CPU with no install. Results stay as open formats (Parquet/JSON) that remain queryable outside the app, and the SQL tab exposes them directly.
  - *Alternatives:* Streamlit/Dash/Shiny (need a Python or R runtime on every laptop; not architecture-neutral); Electron/Tauri (heavy, or platform-specific toolchains); pre-rendered static HTML (no search over 7M rows); Datasette (Python runtime).
- **Launcher:** a dependency-free Go program, cross-compiled from the Mac for Windows x64 (`-H windowsgui`, icon via go-winres) and macOS (universal arm64 + x86_64 `.app`, ad-hoc signed). It embeds the built viewer, finds `wgs-data/releases` by walking up from its own location (or `--data` / `WGS_RELEASES`), serves both on `127.0.0.1` with Range support, opens the default browser, and refuses dotfiles and AppleDouble `._*` files. Port 8787 is preferred; if another instance already answers, it just opens a browser tab. The page sends a heartbeat every 10 s and the launcher exits about 75 s after the last one.
  - *Why a local server at all:* browsers block `fetch`/WebAssembly workers from `file://` pages, so double-clicking an `index.html` cannot work reliably. A single static binary is the simplest thing that works on both laptops with nothing installed.
  - DuckDB-WASM's "eh" bundle is used, which needs no cross-origin isolation headers.
- **Builds** run on the analysis Mac (`pixi run build-dashboard`) in internal scratch space, because exFAT has no symlinks for `node_modules/.bin`. Node and Go come from the pixi environment.

## ADR-012 Local knowledge store, refreshed by version

- **Privacy rule:** knowledge is downloaded and joined to your variants **on this computer**. Variants are never sent to web APIs (no VEP REST, no MyVariant.info). Links out (gnomAD, ClinVar, dbSNP) are only opened if you click them.
- **Sources (all free; versions are recorded per release):**

  | Source | Used for | Size | Update cadence |
  |---|---|---|---|
  | ClinVar (GRCh37 VCF) | Classifications, review stars, conditions | ~180 MB | Weekly |
  | Ensembl GFF3 GRCh37.87 | Gene models for `bcftools csq`; gene search | ~50 MB | Frozen (GRCh37) |
  | ClinGen gene validity + dosage | How strong each gene–disease link is; inheritance | ~2 MB | Daily export, rebuilt only on content change |
  | 1000 Genomes phase 3 sites (v5b, NCBI mirror — EBI is ~30× slower) | Overall and continental allele frequencies | ~2 GB | Frozen |
  | gnomAD v2.1.1 (slivar gnotate) | Popmax AF across about 140k people | ~2.2 GB | Frozen for GRCh37 |

- **Store:** `wgs-data/knowledge/<source>/<version>/` holds Parquet tables. `knowledge/index.json` records the upstream URL, Last-Modified/ETag/size fingerprint, build time and table checksums of each version, plus which version is *current*. A refresh `HEAD`s each source and rebuilds only those whose fingerprint changed. It builds into `.building/` and renames on success, so a failed download never corrupts the current version. The last 4 versions are kept, and the current one is never pruned. `--pin clinvar=YYYYMMDD` reproduces an archived ClinVar release, which makes past results reproducible.
- **Consequences:** `bcftools csq` (haplotype-aware, about 1 minute genome-wide) with Ensembl GFF3. *Rejected:* VEP with a 24 GB cache (too heavy for a portable drive) and snpEff (needs Java plus a 1 GB database, and its HGVS doesn't add much here). echtvar would be ideal for gnomAD, but it has no GRCh37 archive and no osx-arm64 build. slivar's gnotate zip provides the same lookup.
- **Release diff:** `publish` records the knowledge versions and evidence-model version in each manifest, and computes `changes.json` against the previous release. It lists sources whose version changed, claims added, removed or changed (field by field), and every ClinVar reclassification among your alleles. The diff is computed *after* the release digest, so it can never trigger a release on its own.
- **Why:** this fulfils "not a snapshot". Each finding traces back to a dated source version, and each change has a visible cause.

## ADR-013 Evidence model: two grades, weaker wins

- **Problem:** a variant "meaning something" depends on two independent questions. How strong is the published evidence for its effect? And is your genotype really there? A strong ClinVar classification on a low-quality call is not a strong finding, and neither is a perfect call of a 0★ assertion.
- **Decision:** every claim (`claims` table) carries an **evidence grade** (Strong / Moderate / Limited), a **call confidence** (High / Medium / Low / Not callable) and an **overall** grade = the weaker of the two. Each grade has a list of plain-language **reasons** and a list of **sources** with versions. Rules live in `src/wgs/evidence.py` (`MODEL_VERSION`). Changing a rule bumps the version, and the release diff shows its effect like a data update.
- **Evidence grade (v1, ClinVar-based claims):**
  - Review stars: 3–4★ → Strong; 2★ → Moderate; 0–1★ → Limited.
  - *Drug response* caps at Moderate until checked against CPIC/DPWG (Step 5). *Conflicting* → Limited.
  - Pathogenic or likely pathogenic, with population allele frequency (gnomAD popmax, otherwise 1000 Genomes) ≥ 5% → Limited (ACMG BA1). ≥ 1% → down one step (BS1-like).
  - Gene–disease validity in ClinGen *Disputed/Refuted* → Limited. *Limited* → down one step.
- **Call confidence:**
  - Non-PASS → Low.
  - GQ ≥ 30 and DP ≥ 15 → High. GQ ≥ 20 and DP ≥ 10 → Medium. Otherwise Low.
  - Unexpected read balance (het outside 20–80%, hom < 80%) → down one step.
  - Disagreement with the provider's genotype file (SNVs) → Low.
- **Which variants become claims:** ClinVar pathogenic, likely pathogenic, risk factor, association, protective and drug response; conflicting only when a submitter said pathogenic. VUS and benign are never claims; they stay visible in the variant explorer.
- **Routing to sections:**
  - Drug response → Medicines.
  - Association → Traits.
  - Pathogenic, likely pathogenic or conflicting in one copy of a gene whose ClinGen inheritance is recessive-only → Carrier.
  - Everything else → Health.
  - Steps 4–6 add curated claims (ACMG SF genes, CPIC diplotypes, GWAS/PGS traits) with their own evidence rules into the same table.
- **Sensitive findings:** pathogenic or likely pathogenic, and anything in genes such as *BRCA1/2*, *APOE*, *HTT* and *PRNP*, are masked until you click to reveal (per browser session). Each comes with a note that most such findings in healthy people are carrier status, low penetrance or misclassification, and need clinical confirmation.
- **Alternatives considered:** a single numeric score (hides *why*); full ACMG/AMP automated classification such as InterVar (it over-calls without the lab evidence, and is still a black box to a learner); copying ClinVar labels verbatim (ignores call quality and population frequency, both of which caught real problems in testing).

## ADR-014 Health and carrier: inheritance, per-lab conditions, actionability and predictions (evidence model v2)

- **Problem:** with v1, a ClinVar "pathogenic" label went straight into a claim. Three things made that misleading for one person's genome. (1) ClinVar's merged record names every condition any lab mentioned, and some labs list every disease of the gene, so *GJB2* W77R showed dominant skin syndromes next to the recessive hearing loss it is actually known for. (2) Whether one copy matters depends on how the *specific* condition is inherited, not on the gene. (3) Rare variants no lab has classified were invisible, even when every predictor agrees they are damaging.
- **Decision:**
  - **Curated knowledge added** (all downloaded and joined locally): Mondo (disease names and cross-references), HPO and Orphanet (inheritance per disease, gene–disease links), ClinGen dosage and actionability, the ACMG SF v3.3 gene list with each gene's reporting rule (`src/wgs/knowledge/data/acmg_sf_v3.3.csv`), and ClinVar's per-lab `submission_summary` (about 6.8M submissions).
  - **Which condition is meant:** for each variant, each lab submission votes for the conditions it names. Submissions naming one or two conditions count; gene-wide lists do not. Conditions with at least 20% of the top condition's support are kept; the rest are shown as "also listed". The "Who says so" table shows every lab, its verdict and date.
  - **Inheritance:** per condition from HPO/Orphanet via Mondo cross-references, falling back to the gene's modes. Combined with zygosity and sex chromosome this gives a **role**: *carrier*, *affected* (both copies, or the only X copy), *possible* (dominant), or *unknown*. Mixed genes (e.g. *SDHA*: recessive complex II deficiency and dominant paraganglioma) get a per-condition role and a statement that explains both. Only "disease-like" claims (P/LP, conflicting, predicted) get a role; risk factors and associations don't.
  - **Routing:** disease-like and carrier role → Carrier; otherwise Health groups *monogenic*, *compound* (two P/LP variants in one recessive gene — flagged as "possible", since we can't tell if they're on different copies), *predicted*, *uncertain* (conflicting) and *risk* (risk factor, protective, low penetrance). Blood-group "phenotypes" go to Traits.
  - **ACMG SF:** a P/LP claim in a listed gene is *reportable* only if it meets the gene's rule (biallelic for recessive genes, *HFE* only homozygous C282Y, *TTN* only truncating). The `acmg_genes` release table also records the callable fraction of each gene, so "no findings" comes with how much was actually readable.
  - **Computer predictions** (AlphaMissense, REVEL, gnomAD v4.1 constraint) apply only to rare (< 0.1% in every population), PASS variants in known disease genes that ClinVar hasn't classified (or calls benign). Flag if LoF in a gene with LOEUF < 0.6 or a recessive gene, or if REVEL ≥ 0.644 and AlphaMissense > 0.564 agree, or if REVEL alone reaches the "strong" level (≥ 0.932), or (when REVEL has no score) AlphaMissense ≥ 0.9. Always **Limited**: predictors are about 90% accurate on known variants, which still yields many false alarms across a genome. Thresholds follow Pejaver et al. 2022 (ClinGen SVI calibration).
- **Rebuilds:** changing a knowledge source's parsed `schema` forces a rebuild on the next refresh; changing claims logic bumps the annotate stage version so `wgs run` re-annotates automatically.
- **Alternatives considered:** OMIM (best inheritance data, but licensed — HPO/Orphanet cover the same diseases openly); automated ACMG classification such as InterVar or CPSR (over-calls without lab evidence and hides the reasoning); CADD instead of REVEL (genome-wide but less calibrated for missense; its licence also forbids redistribution); SpliceAI (useful, but the precomputed scores need an Illumina login — a candidate for later).

## ADR-015 Pharmacogenomics: PharmCAT with outside calls, GRCh37 positions lifted one by one

- **Problem:** turn the genome into drug-gene results a clinician would recognise, with the published guideline behind each one. Four complications: the data is GRCh37 while PharmCAT only accepts GRCh38; *CYP2D6* cannot be read from a VCF (pseudogene *CYP2D7*, deletions, duplications, hybrids); HLA types need a dedicated typer; and the guidelines change several times a year.
- **Decision:**
  - **PharmCAT 3.4** (the CPIC/ClinPGx reference implementation, used by clinical labs) does diplotype calling, phenotype translation and guideline matching. It runs as a pinned jar from the knowledge store (`pharmcat` source), which also supplies its ~1,200 defining positions. Upgrading PharmCAT is a knowledge refresh, so new guidelines show up on **What changed** like any other source.
  - **No whole-VCF liftover.** PharmCAT warns that lifted VCFs give wrong calls (strand flips, missing reference blocks). Instead each defining position is lifted on its own (UCSC chain), its REF is checked against our verified GRCh37 FASTA (swapped REF/ALT handled), and the genotype is written from our own data: a variant if called, a confident reference *only if the position is callable*, otherwise missing. Missing positions are reported per gene, so "not found" never silently becomes "normal". The 1,226 positions and their status are published as `pgx_positions`.
  - **Outside calls:** *CYP2D6* from the CRAM via **Cyrius** (copy-number aware; run in its own pixi environment, about 20 min); HLA-A/B (and class II for later steps) from the CRAM via **T1K** against IPD-IMGT/HLA (`imgt_hla` source); *MT-RNR1* from mitochondrial variants, where coverage "HIGH" counts as callable. Pre-computed Cyrius/T1K outputs dropped into the WGS folder are ingested instead, so Linux users can run the tools elsewhere.
  - **Grading:** evidence is **Strong** for genes with a CPIC guideline and **Moderate** otherwise (DPWG-only); FDA label text is shown but not graded. Call confidence is **High** from callable VCF positions, lowered for missing positions, and **Medium** for Cyrius/T1K. Cyrius was validated on Illumina data, not DNBSEQ. Overall is the weaker of the two, as everywhere else (ADR-013).
  - **"Guidance differs" vs "standard":** *superseded by ADR-016* (buckets now follow ClinPGx's curated flags, not the wording). Originally: a guideline row was *action* when PharmCAT flags a dosing change or alternative drug, unless its text was a recognised "use standard dose" phrase. *CFTR* rows never count as action when the *CFTR* result is reference: those guidelines only apply to people with CF. Result for this genome: 52 action rows and 101 standard rows.
  - Genes whose guidelines use the genotype directly (VKORC1, CYP4F2, IFNL3) are labelled "Genotype reported", not "No result".
- **Alternatives considered:** Stargazer/Aldy/StellarPGx (more genes from BAMs, but less maintained or with licence limits; Cyrius is the most accurate open *CYP2D6* caller in published benchmarks); a full CrossMap VCF liftover (rejected per PharmCAT's own guidance); HLA-HD or OptiType (HLA-HD needs registration; OptiType is class I only and needs a MILP solver; T1K is MIT-licensed, fast and covers both classes); hand-maintaining CPIC tables (PharmCAT already packages them, versioned).
- **Licences:** PharmCAT MPL-2.0; ClinPGx data CC BY-SA 4.0; IPD-IMGT/HLA CC BY-ND 4.0; Cyrius GPLv3 (run as a separate tool, not linked); T1K MIT.

## ADR-016 No hand-written medical content; buckets from curated flags; release self-checks

- **Problem:** one question about warfarin exposed two bugs and a hand-written note in the viewer. An audit of all 397 guideline rows then found the "standard" test (a regex on the recommendation's wording) wrongly filed DPWG venlafaxine ("It is not possible to offer… Avoid venlafaxine"), codeine, tramadol and propafenone as standard. The viewer also held hand-written one-line descriptions of all 23 medicine genes. Hand-written text can't be refreshed, cited or checked, and won't scale to the next sections.
- **Decision:**
  - **No medical statements written into the app.** Everything the dashboard says about a gene, drug or variant comes from a versioned knowledge source and carries its citation. The viewer may contain teaching text (what a metaboliser type is) and presentational labels, never lookup tables of medical facts keyed by gene or drug. A test (`tests/test_checks.py`) fails if such a table reappears.
  - **Gene descriptions:** MedlinePlus Genetics (written for the public, expert-reviewed; bulk XML) first, then NCBI Gene's summary. RefSeq and OMIM summaries are curated; Alliance summaries are machine-generated, can describe an unrelated overlapping product (MT-RNR1's describes the humanin peptide), and so are shown collapsed and labelled. The official gene name is always shown. Published as `gene_about`.
  - **Drug buckets from structured flags.** ClinPGx curates three flags on every recommendation: `dosingInformation`, `alternateDrugAvailable` and `otherPrescribingGuidance`. **Guidance differs** = either of the first two; **Worth knowing** = only the third (monitoring, "if no response, switch", a dose calculator), or a drug-level note with no single recommendation (CPIC warfarin's flowchart); **Standard** = none, or the guideline says "no recommendation". **Not for your result** = a guideline or label exists, but has no advice for this genotype; such drugs are listed rather than hidden. Only CPIC/DPWG rows set the bucket: FDA label flags describe the label, not the person (desflurane's label is flagged even for a normal *RYR1*). When CPIC and DPWG disagree, the drug takes the more cautious bucket and shows "guidelines differ". Result for this genome: 35 differ, 23 worth knowing, 47 standard.
  - **Release self-checks.** `src/wgs/checks.py` holds SQL rules run on each release's own tables before publishing: findings are sourced, graded and uniquely identified; drug-response findings are never hidden as sensitive; common variants (> 5%, ACMG BA1) are never graded above Limited for disease; matched guidelines have text; buckets match the flags; notes come only from guidelines; every medicine gene has a sourced description. Results go into `checks.json` and the Data quality tab. A failure doesn't block a release (the rest of the data is still useful) but is shown prominently. On their first run they caught two real bugs: duplicate finding ids (DPWG publishes separate per-gene rows for the same drug) and PharmCAT data caveats being treated as drug advice. **Every future bug gets a check**, so it can't return silently.
- **Alternatives considered:** keep a better regex (wording varies across guideline sources and versions; the flags are curated for exactly this purpose); write gene descriptions by hand or with an LLM (not citable or refreshable); fail the release on a check failure (would leave the user with nothing after a knowledge refresh; showing the failure is more useful).
- **Licences:** MedlinePlus and NCBI Gene are US-government works in the public domain.


## ADR-017 Traits and polygenic scores: PGS Catalog + 1000 Genomes percentiles (evidence model v3)

- **Problem:** traits, common-disease risk and brain-related results come from many small effects, not one classified variant. They need a different source, a different way to compute "your result", and a different evidence grade, still with no hand-picking that can't be explained.
- **Decision:**
  - **Single-variant traits** come from the GWAS Catalog (EBI): a short featured list (`knowledge/data/gwas_featured.csv`) of variants with large, replicated effects that people can check against themselves. Your genotype is read with the PGx genotyper (so "no variant" at a well-covered site counts as a call). The effect direction is read from the Catalog's own convention: a "unit increase/decrease" note marks a per-copy β; otherwise the number is an odds ratio. The share of people with your genotype comes from 1000 Genomes allele frequencies (Hardy–Weinberg). Where the Catalog does not record the effect allele, the result is shown but graded Limited.
  - **Polygenic scores** come from the PGS Catalog. **Selection rule** (`knowledge/pgs.py: select`): for each trait, the single-trait score tested by the most *independent* publications, then the most independently tested people, then the most tested people, then the newest. About 45 featured traits get a page section and body system; every other trait with at least one independent test is browsable. Two pins override the rule, each with a reason in the CSV: multiple sclerosis (PGS002726: the rule's top picks split the genome into an HLA-only and a non-HLA score, so a whole-genome score is the fairer summary) and age-related macular degeneration (PGS004606: the rule's pick is the African-ancestry-trained twin of this European-trained score; swap if the Ancestry section shows a different closest population).
  - **Computing percentiles** follows pgsc_calc (the PGS Catalog's own pipeline) step by step, run locally with `pgscatalog-utils` and `plink2` in a separate pixi environment: QC the 1000 Genomes reference (GRCh37 harmonised panel, KING-related samples removed), build a target file of your genotypes at every score position (callable reference sites included), project you onto the reference PCs, normalise and match each scoring file, score you and the panel, then `ancestry-adjust` picks the most similar super-population and reports your empirical percentile in it.
  - **`--keep_ambiguous`:** pgsc_calc drops strand-ambiguous (A/T, C/G) SNPs by default because array data may be on either strand. Here both your calls and the harmonised scoring files are on the GRCh37 forward strand, so they are kept; without this 14 of 140 scores fell below the 75% match threshold.
  - **Evidence model v3** (`evidence.py`): GWAS single variants: Strong ≥ 3 publications, Moderate 2, Limited 1, or if below genome-wide significance, or if the effect allele is unknown. Polygenic scores: Moderate when ≥ 2 independent publications tested it in ≥ 20,000 people, otherwise Limited — **never Strong**, because a score shifts odds modestly and never diagnoses. Call confidence: High ≥ 90% of variants matched, Medium ≥ 75%, else Not callable (and no percentile is shown). Each score shows its best evaluation (independent first, then one reporting an effect size, then the largest).
  - **Brain & mind** is its own section with a caveats panel (weak prediction, confounding by family environment for education/cognition scores, European bias). Rare damaging-predicted variants in SFARI Gene genes are listed, always Limited, mirroring the Health page's prediction rules.
  - **Self-checks:** trait positions lift sanely, every trait and score is graded, direction-unknown SNPs are Limited, match rates of scored scores ≥ 75%, percentiles are within 0–100, every featured score is scored, no score is Strong, genotype calibration (see below), and score spread (across ≥ 20 scores the mean z must be within ±0.5 and the SD within 0.6–1.5; a systematic genotyping error shows up as a shifted or squashed distribution long before any single score looks odd).
  - **Stand-ins (alternates):** the rule also records the next two ranked scores for each featured trait. If the rule's pick cannot be scored on your data (match rate below 75%), the first stand-in that does score takes its place, and the page says so ("Stands in for X …"). This is how LDL cholesterol (rule pick PGS000814, 16 variants, 62.5% matched) is handled without a hand-made exception.
  - **Indels near other variants count as missing, not "no variant":** WGS callers can describe the same insertion/deletion at a slightly different position or as part of a larger multi-base change. Counting the panel's site as "0/0" in that case biased indel calls (18% "0/0" at sites where > 99% of people carry the variant). A panel indel with any of your indels within 25 bp, or inside a multi-base change, is now treated as missing (pgsc_calc mean-imputes missing variants). After the fix indels match SNPs (0.5% "0/0" in that band). The check `pgs.genotype_calibration` keeps this honest on every run: at sites where > 99% of the panel carries a variant, fewer than 2% of your calls may say you do not.
  - **Practical details:** matching runs in batches of at most 400 MB of compressed scoring files, because pgscatalog-match holds every file in memory and 220+ scores were killed on a 16 GB Mac; each score is matched on its own, so results are identical. Reference-panel scoring first copies only the variants the matched scorefiles use (~3 GB instead of the 7 GB, 78 M-variant panel) to the internal disk, once per run (≈ 5 min), then scores each chunk from it (≈ 2 min instead of 30–75 min; verified to give the same sums to the last printed digit). Panel scores do not depend on your genotypes, so they are also cached by a hash of the scoring file and panel version. Panel variants without an ID (`.`) are handled by passing the scoring file's own IDs to plink with `--extract`. macOS writes hidden `._*` files on exFAT drives; every file listing in the stage skips them. plink is given half the machine's memory so a 16 GB laptop does not swap.
- **Alternatives considered:** HIrisPlex-S for eye/hair/skin colour (model parameters are not published; the web tool would send genotypes off the machine, breaking the privacy rule); running pgsc_calc itself (Nextflow + containers; not portable to Windows and heavier than the pieces it wraps); one hand-picked score per trait (not refreshable or explainable); comparing to all 1000 Genomes samples (percentiles shift with ancestry for technical reasons).
- **Cost:** first run ≈ 2–3 hours on a 16 GB Mac with the data on an external SSD (reference QC 14 min and score normalising 34 min are cached per panel/catalog version; matching ≈ 40 min uses ~10 GB of temporary space on the internal disk; scoring the reference panel ≈ 20 min via a subset copy, cached). Re-runs after a catalog refresh redo only normalise/match and the scoring of changed score files; re-runs on the same catalog take minutes.
- **Licences:** GWAS Catalog and PGS Catalog metadata are EMBL-EBI open data; each scoring file's licence is recorded with the score. 1000 Genomes is open access. SFARI Gene data is free for research use.


## ADR-018 Verification audit: exact sources, live re-checks, ACMG BA1, and risk in absolute numbers (evidence model v4)

- **Problem:** before adding more sections, a review of every finding asked three things: does each finding link to the exact record it came from, does that record still say what we say, and what does a result mean in real outcomes ("8 in 100 vs 1 in 100", not "1.4× odds")? The review found eight bugs: the F5 Leiden site read backwards (GRCh37's reference carries the Leiden allele); a "belongs to the rarer allele" note that contradicted ClinVar on alt-major sites; common alleles (≥ 5%) given carrier/affected labels; protein changes in nonstandard notation; VUS wording claiming no lab had classified a variant ClinVar lists as uncertain; intergenic GWAS hits with no gene; brain variants without sources; and PGS cards saying "N variants found" when they meant positions readable.
- **Decision:**
  - **Exact records.** Every finding's `sources` lists the record (ClinVar VCV, GWAS Catalog GCST + PubMed, PGS Catalog PGS/PPM, SFARI gene page, gnomAD variant, MANE transcript). Protein changes are HGVS on the MANE Select transcript (Ensembl/NCBI MANE v1.x), e.g. `p.Asn314Asp on NM_000155.4`. Self-checks enforce that each claim links to a record (a URL with an id, not a home page), brain variants and trait variants are sourced, and protein names match `^p\.`.
  - **ACMG/AMP BA1** (`evidence.too_common`): an allele at ≥ 5% in any population is too common to cause a rare Mendelian disease on its own, so carrier/affected labels are withheld (role "Too common to cause it alone") and the evidence grade drops to Limited. ClinVar expert-panel/practice-guideline records (3★+) are exempt because ClinGen already weighed frequency (its BA1 exception list includes HFE C282Y). Self-check `claims.ba1_role`.
  - **Live audit** (`wgs audit`, `src/wgs/audit.py`): re-fetches every cited ClinVar record (classification + review stars; "changed upstream" when ClinVar re-evaluated it after our snapshot), GWAS Catalog association (study + effect allele), PGS Catalog score (trait + publication), PubMed citation (title), a sample of links, and every curated quote (below). The report goes to `wgs-data/audits/` and a summary beside the releases (`releases/audits/<id>.json`) that the Data quality tab shows. It needs internet, so it is a command rather than a pipeline stage; run it after every refresh. First run: ClinVar 264/264, PGS Catalog 141/141, PubMed 134/134, GWAS Catalog 15/15 matched; 1 dead link (an HPO purl that now redirects to a removed page), fixed by linking ontology terms through EBI OLS.
  - **Absolute risk for polygenic scores** (`src/wgs/absrisk.py`) — two automated routes and one curated input:
    1. *From discrimination (AUROC)*: AUROC is unit-free, so it can be converted without knowing how the study scaled the score. Under the binormal liability model, `d = √2·Φ⁻¹(AUROC)` and the risk at your z is solved exactly against the baseline K. Only evaluations whose covariates are purely technical (ancestry PCs, genotyping batch), with ≥ 1,000 people and ≥ 100 cases, for the score's own disease (not a subtype, special population or "10-year risk" model), and in the ancestry you were compared with, are used — independent studies first, then the largest.
    2. *From a per-SD odds or hazard ratio*: only where a curated row confirms the ratio is per standard deviation (≈ 0.6% of PGS Catalog records say so; the field has no unit). The logistic model is calibrated so the population average equals K (Gauss–Hermite integration); hazards use `1 − exp(−H·e^{βz})`.
    3. *Baseline K*: a cited lifetime risk from `knowledge/data/baseline_risk.toml` (each row: value, CI, age window, population, source URL, PubMed id and the exact quoted sentence) — else the evaluation cohort's own case share, labelled as such, only when the cohort was not enriched for cases (≤ 20% cases).
    The card shows "≈ X in 100 people with your score (range from the effect's CI) vs Y in 100 typical", the ratio, both sources with links and quotes, the method, and a reminder that lifestyle and family history matter as much. Otherwise it says **not established** with the specific reason. Sex-specific scores show "not applicable" for the other sex. Self-check `pgs.abs_risk_sourced`; the audit's `curated` check confirms each quote's numbers still appear at its source.
  - **Single-variant findings:** for P/LP findings where you may be affected, the ClinGen Actionability expert panel's likelihood score is shown as a band ("5 to 39 in 100 people with a disease-causing genotype develop …", with its evidence grade A–D). ClinVar gives no effect size for risk factors, so no number is invented for them.
- **Alternatives considered:** OR per allele × population risk for every variant (ClinVar has no ORs; GWAS ORs are per allele and not additive for monogenic variants); using PGS Catalog ORs as if per SD (the unit is usually unknown; a per-quintile OR read as per-SD inflates risk several-fold); taking lifetime risks from a single global source such as GBD (licence and age-window mismatches); an LLM summary per finding (not citable or checkable).
- **Known limitation:** pathogenic variants where GRCh37's reference carries the disease allele (F5 Leiden-type) are absent from ClinVar's GRCh37 VCF and so can't be found from your VCF alone; the F5 card explains this.
- **Addendum (hardening after the first full audit):**
  - *A value must be in its quote.* A baseline row is used only if its quoted sentence states the value (as a percent, per 1,000/100,000 or "1 in N"); rows whose quote only pointed to a supplement, or whose value was derived by us (e.g. summing subtypes), were removed.
  - *Per-SD rows need four confirmations:* the PGS Catalog performance record (PPM) reports the same ratio (±0.005); its cohort ancestry matches yours; its covariates are only age, sex or technical terms; and the paper's quoted text says the ratio is per SD. The "not established" reason names the rule that failed. Effects confirmed this way are labelled "per standard deviation of the score" everywhere; other ORs/HRs say "between score groups" or "comparison not stated in the PGS Catalog".
  - *Gene-specific penetrance only from single-gene ratings.* ClinGen sometimes rates several genes together (121 of 443 reports); a band from such a report is not shown for any one gene; the card says which genes it was shared with. Self-check `claims.penetrance_single_gene`.
  - *Audit robustness.* Transient failures (PMC stub pages, Ensembl 504s, NCBI 400s) are retried before being reported; numbers are normalised (Lancet middle dots, thin spaces, HTML entities) before matching quotes.
